# Soroka24 — клиентский сервис

Обычный Django: пользователи, аутентификация, подписки, UI. Ни DRF, ни SPA (ТЗ §13).

**Судебных данных здесь нет.** Ни `Case`, ни `CaseEvent`, ни `CourtSession`, ни `Document` —
всё это живёт в `core_v2` и берётся у него по HTTP в момент показа. Копия судебной модели в
двух сервисах означала бы, что правка парсера требует миграции здесь, а расхождение копий
никто не заметит.

## Граница ответственности

```
        этот сервис
        кто на что подписан, что кому показано, UI
              │                                        ▲
      какие дела интересны                    что изменилось
      PUT /monitoring/cases                   RabbitMQ, очередь case_changes
              ▼                                        │
        core_v2
        суды, дела, поход на портал, разбор, регулярный обход
```

Одной строкой: **мы знаем, какие дела интересны; core знает, как и когда их обновлять.**

Обратное тоже верно и важно: этот сервис не знает, как устроены сайты судов, и знать не
должен. Ни одного правила про порталы здесь нет — даже «это ссылка или УИД?» решает core.

## Модели

Их две, и обе про нас, а не про суды:

| Модель | Что означает |
|---|---|
| `CaseSubscription` | пользователь следит за карточкой дела в core (`core_case_id`) |
| `PendingCaseSearch` | пользователь ждёт ответа по ссылке: дела ещё нет, подписки ещё нет |

`UserCaseChange` (unread) добавится в Phase 6.

**Почему нужен `PendingCaseSearch`.** Между «добавил» и «нашли» проходит 30–60 секунд: core
в это время идёт на портал через прокси и разгадывает капчу. Без строки в базе ожидание
жило бы только в открытой вкладке — закрыл её, и подписка не создалась бы, хотя дело в core
уже появилось. Пользователь при этом уверен, что дело добавил.

Развязывают ожидание оба пути: страница ожидания (быстрый, пока вкладка открыта) и
`manage.py resolve_pending_searches` (медленный, для закрытых вкладок).

**Внешних ключей на дела нет и быть не может** — они в другой базе. Значит, `core_case_id`
может указывать на карточку, которой уже нет; заметить это — наша забота. Ответ
`PUT /monitoring/cases` возвращает для этого `unknown_ids`.

## Страницы

Стандартные Django CBV, своей иерархии классов нет (ТЗ §13):

| Страница | CBV | Особенность |
|---|---|---|
| Вход | готовая `LoginView` | через `django.contrib.auth.urls`, своей вьюхи нет |
| Мои дела | `ListView` | витрины всех дел ОДНИМ запросом к core |
| Добавить дело | `FormView` | ветвление по пяти исходам `POST /search_case` |
| Ищем дело | `DetailView` | обновление метатегом, без JS |
| Дело | `DetailView` над ПОДПИСКОЙ | судебные данные из core в `get_context_data` |

`DetailView` над подпиской, а не над делом, — потому что Django-модели `Case` здесь нет.
Побочная выгода: проверка прав достаётся бесплатно (queryset ограничен своими подписками),
и забыть её нельзя — её просто нет как отдельного кода.

**Отказ core нигде не превращается в 500.** Недоступность соседнего сервиса — ожидаемое
состояние: список подписок наш, и показать его надо даже когда core молчит. Пустая страница
выглядела бы как «дела пропали».

## Интеграция с core

Вся в `cases/integrations/core.py`, простыми функциями на `requests`. Смысл модуля не в
переиспользовании, а в границе: `requests` во views не появляется, иначе таймауты и знание
об адресах core расползутся по обработчикам.

Тонкость: `POST /search_case` отдаёт **422 с полезным телом** («не тот формат УИД», «этот
портал не поддержан»), поэтому список осмысленных кодов задан на каждую ручку отдельно.
Трактовать такое как аварию значило бы показать «сервис недоступен» вместо внятного
объяснения, что не так со ссылкой.

Текст отказа приходит с сервера **готовым** и показывается как есть: он знает про
конкретный участок («Судебный участок № 235: поиск по УИД тут не поддерживается»).
Сочинять свой — терять эти подробности.

## Синхронизация мониторинга

`cases/monitoring.py`. Из подписок строится distinct-список и уезжает в core одним `PUT`:

```python
CaseSubscription.objects.filter(is_active=True).values_list("core_case_id", flat=True).distinct()
```

`distinct` обязателен, и это не оптимизация запроса. На дело с тремя подписчиками core
должен сходить ОДИН раз: поход стоит прокси и оплаченной капчи.

Зовётся сама — после подписки и отписки, ПОСЛЕ коммита транзакции (иначе core получил бы
список без только что созданной подписки). Отказ core её не роняет: подписка уже записана,
а расхождение снимет следующая синхронизация. В логе при этом остаётся WARNING — «дела не
обновляются» начинают разбирать именно с него.

Отписка от последнего дела передаёт `force`: пустой список core иначе отклонит с 409, и
последнее дело осталось бы на обходе навсегда.

## Подписка на изменения

`manage.py consume_case_events` — постоянно работающий процесс (контейнер
`client-consumer`). Держит соединение с RabbitMQ открытым, и брокер отдаёт факт изменения
сразу, как только core его опубликовал. Опроса раз в минуту здесь нет: он и медленнее
(изменение ждёт впустую), и дороже (шестьдесят пустых запросов вместо одного соединения).

Сообщение выглядит так и судебных данных не несёт:

```json
{"id": 1502, "type": "event_new", "version": 1,
 "case_id": 481, "entity_id": 712, "occurred_at": "2026-08-23T13:20:00+00:00"}
```

«По делу 481 появилось новое событие, его id 712». Понадобятся подробности — заберём по
HTTP. `id` — идентификатор СООБЩЕНИЯ: на нём будет держаться идемпотентность в Phase 6,
потому что доставка at-least-once.

Разбор живёт в `cases/consumer.py` отдельно от команды: там транспорт, здесь решение.
Три исхода, и разница между ними не формальность:

| Исход | Что делаем | Когда |
|---|---|---|
| `PROCESSED` | `ack` | обработали |
| `MALFORMED` | `ack` | выбросили ОСОЗНАННО |
| `RETRY` | `nack(requeue=True)` | не смогли, но сможем позже |

**Мусор выбрасывается, а не возвращается в очередь.** `nack(requeue=True)` на непонятном
сообщении вернёт его нам же, мы снова не поймём — и так навсегда, забив очередь одним
битым сообщением и заблокировав все настоящие изменения. Поэтому `MALFORMED` — это `ack`
с громким WARNING в логе.

Реплик может быть несколько, в отличие от publisher'а в core: RabbitMQ отдаёт каждое
сообщение одному подписчику.

### Проверить руками

```bash
docker compose logs -f client-consumer
# в другом терминале изменить дело в core — сообщение появится в логе через секунду

# разово, с выходом после N сообщений:
docker compose run --rm --no-deps client-consumer python manage.py consume_case_events --limit 1
```

`--limit` берёт РОВНО столько: prefetch на это время урезается до лимита, а сообщение,
которое брокер успел отдать сверх него, возвращается в очередь нетронутым. Флаг для ручной
проверки не должен врать о том, что сделал.

### Ловушка с адресом брокера

`INTEGRATION_BROKER_URL` в `.env` записан в привычной для Celery форме
`amqp://…:5672//`. Двойной слэш kombu (то есть core) читает как стандартный vhost `/`, а
**pika — как vhost с пустым именем** и падает с `NOT_ALLOWED - vhost  not found`.
Приведение к понятной pika форме `/%2F` делает `broker_parameters()` в самой команде, чтобы
общий адрес в `.env` остался в единственной знакомой всем форме.

## Команды

```bash
python manage.py migrate
python manage.py createsuperuser
python manage.py sync_monitoring              # сверка: отправить core актуальный список
python manage.py resolve_pending_searches     # добрать ожидания с закрытыми вкладками
python manage.py consume_case_events          # слушать очередь изменений (постоянный процесс)
```

`resolve_pending_searches` запускать по расписанию ОС (cron), раз в минуту достаточно.
Celery здесь не заводим: одна периодическая команда его не оправдывает.

## Запуск

В составе всего каркаса:

```bash
docker compose up -d client-web client-consumer   # http://localhost:8001
```

`client-web` и `client-consumer` идут из одного образа и отличаются только командой.
Миграции накатывает **только** `client-web`: две команды, гоняющие `migrate` одновременно,
боролись бы за блокировку `django_migrations`.

Миграции контейнер накатывает сам при старте. Пользователя надо создать руками:

```bash
docker compose exec client-web python manage.py createsuperuser
```

Локально, вне docker:

```bash
cd services/client
CLIENT_DATABASE_URL=postgres://soroka:soroka@localhost:5432/soroka_client \
  ../../.venv/Scripts/python.exe manage.py runserver
```

## Тесты

```bash
cd services/client && ../../.venv/Scripts/python.exe -m pytest -q
```

Нужен настоящий PostgreSQL — тестовую базу Django создаёт сам. core в тестах подменяется
целиком: живого backend'а им не нужно, а нужно, чтобы каждая ветка ответа приводила к
правильному состоянию.

Три теста стоит знать по именам, потому что они охраняют решения, а не поведение:

* `test_no_court_tables_in_the_schema` — судебных таблиц в базе клиента нет;
* `test_my_cases_asks_core_once_for_many_cases` — тридцать подписок = один запрос к core.
  Регресс здесь ничего не сломал бы видимо, страница просто стала бы линейно медленнее;
* `test_another_users_case_is_not_visible` — чужое дело отдаёт 404 и до core даже не идёт.
