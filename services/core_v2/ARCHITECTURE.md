# Как устроен core_v2

Документ для того, кто открывает проект впервые. Задача — чтобы вы могли **сами**
проследить любой путь по коду, не спрашивая никого.

Читать можно двумя способами: сверху вниз целиком либо ныряя в нужный вопрос по
оглавлению. Каждый ответ ссылается на конкретный файл и функцию — открывайте и смотрите.

---

```
                  ╱          ╲
                 ╱            ╲
       метаданные навигации    HTML
       (номер дела, участок)     │
                 ╲             ╱
                  ▼           ▼
              КАКАЯ ЭТО КАРТОЧКА?
              суд + УИД + номер дела
              app/services/identity.py
                      │
                      ▼
             get_parser(portal, html)
             app/parsers/__init__.py
                      │
                      ▼
                  CaseParser  ──── «что внутри страницы?»
                  app/parsers/
                      │
                      ▼
                  ParsedCase
                      │
                      ▼
                   sync_case
                   app/services/case_sync.py
                      │
              ┌───────┴────────┐
              ▼                ▼
         PostgreSQL       CaseChanges
                               │
                               ▼
                          OutboxEvent
                          app/outbox.py
```

Каждый блок здесь — **не обязательно класс**. `get_parser` и `resolve_case_uid` — обычные
функции. Класс появляется там, где есть состояние или несколько реализаций.

Три вопроса, на которые отвечают три разных места, и путать их нельзя:

| Вопрос | Кто отвечает |
|---|---|
| Как добраться до страницы? | `CourtClient` (`app/courts/`) |
| Какую именно карточку мы получили? | identity (`app/services/identity.py`) |
| Что написано внутри страницы? | `CaseParser` (`app/parsers/`) |

## 1. Где начинается FastAPI application?

`app/main.py:16` — там создаётся `app = FastAPI(...)`, подключаются четыре роутера и админка.

Роуты лежат в `app/api/`, разложенные по смыслу запроса, а не по модели:

| Файл | Роуты |
|---|---|
| `app/api/search_case.py` | `POST /search_case`, `GET /search_case/tasks/{id}` |
| `app/api/cases.py` | `GET /cases/{id}`, `GET /cases/{id}/summary` |
| `app/api/events.py` | `GET /cases/{id}/events` |

Плюс `GET /ping` прямо в `main.py` и админка на `/admin`.

**Важное правило, которое нельзя нарушить:** все обработчики объявлены обычным `def`, а не
`async def`. Походы на порталы идут через Playwright **sync** API, а `sync_playwright()`
падает внутри работающего event loop. FastAPI выполняет обычный `def` в отдельном потоке —
там event loop'а нет. Правило закреплено тестом
`tests/test_skeleton.py::test_all_routes_are_sync`, потому что сломается оно молча.

<a id="2"></a>
## 2. Что делает FastAPI?

Принимает запрос, проверяет входные данные, ходит в репозиторий, собирает ответ. **И
больше ничего.** В портал суда он не ходит никогда.

Причина не в чистоте архитектуры: один поход на портал занимает 25-35 секунд, требует
прокси и платной капчи. Держать HTTP-соединение всё это время нельзя. Поэтому
`POST /search_case` (`app/api/search_case.py:26`) заводит запись `SearchTask`, кладёт
задачу в очередь и **сразу** отдаёт `task_id`. Клиент опрашивает
`GET /search_case/tasks/{id}`, пока не увидит `success` или `failed`.

Что роут всё же проверяет до постановки задачи — и проверяет намеренно:

* формат УИД или адреса (`app/validators.py`);
* есть ли такой суд в справочнике. Если нет — на портал не идём вовсе: прокси и капча
  тратились бы впустую, сохранить карточку всё равно не к чему;
* умеем ли мы вообще открывать этот портал (`is_supported_url`);
* нет ли уже незавершённой задачи по тому же УИД или адресу — чтобы не заводить дубль.

<a id="3"></a>
## 3. Где начинается Celery task?

`app/tasks.py`. Все задачи тонкие:

| Задача | Что делает |
|---|---|
| `run_search_task` | обойти дело по заведённой задаче поиска |
| `resync_case_task` | обойти уже известное дело ещё раз |
| `sync_monitored_cases` | раз в сутки поставить на обход все дела с `is_on_monitoring` |
| `sync_courts_from_json` | залить справочник судов из `data/courts.json` |
| — плюс `enqueue_case_resync` | не задача, а функция: заводит `SearchTask` и кладёт задачу в очередь |

Инстанс Celery — `app/celery_app.py`. Две очереди: `urgent` (свежие дела от
пользователей) и `regular` (всё остальное), плюс одно расписание — ночной прогон дел на
мониторинге (вопрос [24](#24)). Расписанию нужен отдельный процесс `celery beat`, и
ровно один: две реплики дадут двойной обход.

`sync_monitored_cases` от остальных отличается тем, что сама ничего не обходит — она
только ВЫБИРАЕТ дела и зовёт `enqueue_case_resync`. Своей логики синхронизации у
мониторинга нет: обход дела не зависит от того, почему за ним пошли.

Задача отвечает ровно за три вещи, которых нет в самом обходе:

1. **фоновое исполнение** — эндпоинт не может ждать полминуты;
2. **повторы** — временный отказ надо повторить, и с другого прокси;
3. **запись `SearchTask`** — наблюдаемая снаружи ручка: по её id спрашивают «ну что там».

Всё остальное — в `app/services/discovery.py`. В старом core наоборот: тело задачи
занимало 190 строк и делало решительно всё.

**Как задача решает, повторять ли поход.** Обход просто падает исключением, а
классификация живёт одной строкой в `app/services/discovery.py:64`:

```python
TERMINAL_ERRORS = (UnsupportedCourt, CaseNotFound, UnsupportedPage)
```

`is_terminal(exc)` → `True` значит «со второго захода страница будет ровно та же,
повторять бессмысленно». Всё остальное — временное: 403, таймаут, севшая капча.
Реакция — в `_handle_failure` (`app/tasks.py:206`).

Есть одна тонкость с повторами, из-за которой в старом core задачи залипали. Счётчик
попыток проверяется **вручную, до** вызова `retry`: если в `retry(exc=...)` передан `exc`,
то при исчерпании попыток Celery пробрасывает именно его, а не `MaxRetriesExceededError`.
Ловить `MaxRetriesExceededError` бесполезно — эта ветка не срабатывает, и задача остаётся
в `RUNNING` навсегда. А `RUNNING` считается активным статусом, то есть такая задача
навсегда блокирует повторный запрос этого УИД через API.

<a id="4"></a>
## 4. Что такое CourtClient?

Класс, который отвечает на **один** вопрос: как получить страницу карточки с этого
портала. Базовый — `app/courts/base.py:CourtClient`.

Его дело: навигация в браузере, формы поиска, капча, прокси, cookies, ошибки транспорта,
снимок страницы при отказе.

Чего он **не** делает — и это главное отличие от старого core:

* не выбирает парсер;
* не вызывает парсер;
* не разбирает содержимое страницы — ни судью, ни события, ни стороны;
* не арендует прокси (получает готовый аргументом).

Два входа в карточку, потому что порталы устроены по-разному:

* `fetch_cases_by_uid(uid)` — у портала есть поиск по УИД. Отдаёт **список**: поиск
  показывает таблицу, и дел в ней может быть несколько;
* `fetch_card_by_url(url)` — поиска нет, зато карточка открывается прямым адресом. Отдаёт
  одну карточку.

Реализовать нужно только тот, который портал поддерживает; у второго остаётся отказ по
умолчанию.

Три клиента:

| Клиент | Портал | Как добираемся |
|---|---|---|
| `MoscowClient` (`app/courts/moscow.py`) | mos-sud.ru | форма поиска по УИД → перебор строк таблицы → открытие карточки в новой вкладке |
| `MsudrfClient` (`app/courts/msudrf.py`) | msudrf.ru, 63 региона | прямая ссылка + прохождение капчи; сертификат субдоменов невалиден, поэтому `ignore_https_errors` |
| `SpbClient` (`app/courts/spb.py`) | mirsud.spb.ru | прямая ссылка + ожидание, пока Angular дорисует карточку (до 90 секунд) |

<a id="5"></a>
## 5. Как выбирается CourtClient?

`app/courts/resolver.py`. Два словаря и две функции:

* `COURT_BY_PREFIX` (`:116`) — по первым символам УИД. Там только порталы с поиском по
  УИД, сейчас одна строка: `"77MS" → MoscowClient`;
* `COURT_BY_DOMAIN` (`:122`) — по домену ссылки, 64 записи.

`define_court_by_uid` (`:272`) и `define_court_by_url` (`:304`) создают экземпляр клиента.
`portal_for` (`:251`) отдаёт только строку-ключ портала, **не создавая** клиента — она
нужна раньше, до аренды прокси.

**Порядок сверки хоста принципиален** (`_client_for_host`, `:294`): сначала точное
совпадение по границе имени, и только если не совпало — остальные написания хоста
(`host_variants` в `app/validators.py:150`). Если сделать наоборот, `ralt.msudrf.ru`
(Республика Алтай) совпадёт с `alt.msudrf.ru` (Алтайский край), и дело привяжется к чужому
суду в другом регионе. То же с `perm` и `prm`.

<a id="6"></a>
## 6. Почему CourtClient соответствует порталу, а не вёрстке?

Потому что вёрстка — свойство **страницы**, а клиент — про **способ до неё добраться**.
Это разные вещи, и склеивать их дорого.

Живой пример: движок msudrf.ru обслуживает 63 региона и отдаёт **две** разные разметки
карточки. Какую именно — заранее неизвестно: регионы подключают по домену, не открыв ни
одной карточки. У Орловской области оказался тип B, у соседнего Пермского края — тип C.
При этом ходить на портал надо совершенно одинаково: тот же адрес, та же капча, тот же
невалидный сертификат.

В старом core под это было **два класса клиента**, и второй состоял целиком из одной
строки:

```python
class MsudrfTypeCCourtClient(MsudrfCourtClient):
    page_type = "C"
```

Ни одного переопределённого метода. Его же докстринг это признавал: «ходить на портал
здесь нечем отличаться».

Отсюда правило, которое стоит держать в голове при добавлении регионов:

> **Новая вёрстка добавляет ПАРСЕР, а не клиента.**

Новый клиент нужен только тогда, когда меняется сам способ добраться до страницы: портал
завёл форму поиска, сменил вид проверки, стал рисовать карточку скриптом.

У клиентов поэтому **нет** атрибута `page_type` — закреплено тестом
`tests/test_parser_choice.py::test_clients_do_not_declare_a_layout`.

<a id="7"></a>
## 7. Какие метаданные CourtClient может вернуть?

`FetchedCard` (`app/courts/base.py:63`) — страница плюс то, что стало известно **по ходу
навигации**:

| Поле | Кто заполняет |
|---|---|
| `html` | всегда |
| `case_code` | только Москва — номер дела стоит в строке таблицы результатов |
| `participok_no` | Москва (из `href`), Петербург (из пути адреса) |
| `source_url` | ссылочные ветки |
| `status` | HTTP-статус страницы, если его видели |
| `captchas_solved` | сколько платных капч ушло на карточку |

Смысл этих полей — **не выбрасывать то, что портал уже сказал**. Поиск по УИД отдаёт
таблицу, и номер дела с номером участка стоят прямо в её строке, то есть известны РАНЬШЕ,
чем откроется карточка. Это важно: и номер, и суд входят в ключ карточки, а на самой
странице номер приходит под разными метками («Номер дела» у КоАП, «Номер заявления» у
гражданских) и потому не всегда, суда же там нет вовсе.

В старом core `fetch_case_html_by_url` возвращал голую строку HTML, и вызывающий код
собирал карточку обратно вручную, таская адрес и статус отдельными переменными.

**Одно поле намеренно пустое.** У московской ветки `source_url` остаётся `None`, хотя
адрес технически доступен. Заполнить его значило бы завести делам Москвы строки в
`case_url`, которых у них раньше не было, — то есть изменить поведение поиска по адресу.
Это отдельное изменение, и его место не в переносе.

<a id="8"></a>
## 8. Как определяется Court?

**По справочнику, и НИКОГДА из УИД.**

Первые четыре символа УИД — это регион и звено суда, но не сам суд. Собрать код суда
арифметикой нельзя: у 36 московских судов номер участка не совпадает с числом в коде.
Участок № 463 — это код `77MS0466`, а `77MS0463` — совсем другой суд.

Два источника, по тому, как дело попало в систему:

* **дело пришло ссылкой** → по хосту: `_court_by_url` (`app/services/discovery.py:367`) →
  `CourtRepository.get_by_url` (`app/repositories/courts.py:161`). Обычно хватает хоста (на
  msudrf у каждого участка свой поддомен), но у порталов с одним хостом на весь регион
  (Петербург) суд ищется по номеру участка из пути — развилку держит `get_by_url`;
* **дело найдено поиском** → по номеру участка из строки таблицы:
  `_court_by_participok` (`:379`) → `CourtRepository.get_by_participok`
  (`app/repositories/courts.py:80`).

Суд ссылочного дела определяется **до похода на портал** — и это не оптимизация ради
оптимизации: если суда нет в справочнике, карточку всё равно не к чему привязать, а поход
стоит полминуты и платной капчи.

Справочник — 7747 записей, заливается из `data/courts.json`:

```bash
python scripts/sync_courts.py
```

**Без строк `Court` не работает ничего.** Это первое, что делают на свежей базе.

<a id="9"></a>
## 9. Как определяется UID?

`resolve_case_uid` (`app/services/identity.py:64`). Три шага, **порядок обязателен**:

1. **Карточка по этой ссылке в базе уже есть — берём ЕЁ УИД и не меняем никогда.**
2. **На странице есть настоящий УИД — берём его.** Он сквозной и связывает карточки одного
   дела в разных инстанциях (`find_uid`, `app/courts/base.py:35` — одна общероссийская
   регулярка на все порталы, от вёрстки не зависит).
3. **УИД на странице нет вовсе — считаем ключ сами от ссылки** (`synthetic_uid`,
   `app/validators.py:101`).

Для дел, найденных поиском по УИД, ничего разрешать не нужно: УИД там пришёл извне.

Обратите внимание, что доказательством «открылась именно карточка» служит **не** наличие
УИД, а номер дела: его достаёт `resolve_case_code`, и он падает с `CaseNotFound`, если
заголовка на странице нет. Раньше эту роль играл УИД — но его может не быть вовсе.

<a id="10"></a>
## 10. Что происходит с synthetic UID?

Это самое неочевидное место сервиса, и стоит понять, зачем шаг 1 из предыдущего вопроса
написан именно так.

У части карточек УИД на портале нет вовсе: архивные дела движка msudrf.ru, целые регионы
вроде Магаданской области. Опознать их нечем, поэтому ключ считается от адреса:

```
nouid-<код суда>-<первые 12 символов sha256 канонического адреса>
```

`synthetic_uid` (`app/validators.py:101`), проверка — `is_synthetic_uid` (`:126`).

Дальше начинается важное. Портал может **позже дозаполнить** настоящий УИД у дела,
которое мы завели без него. Соблазн — подменить ключ настоящим УИД. Делать этого нельзя:

`Case.card_key` (`app/models/case.py:158`) = `"УИД | код суда | номер дела"`, и от него
считаются детерминированные `uid` **всех** дочерних строк — событий, документов,
заседаний, местонахождений. Сменить ключ значит перестать узнавать всё, что уже сохранено:
следующий обход отчитается «всё удалено, всё создано заново», и в историю дела уедет
волна ложных изменений. Заодно поедет путь снимков страницы в S3.

Поэтому сохранённый УИД побеждает навсегда, а расхождение только пишется в лог. Закреплено
тестом `tests/test_identity_resolution.py::test_real_uid_appearing_later_does_not_rekey_the_card`.

Наружу самодельный ключ **не отдаётся**: `Case.public_uid` (`app/models/case.py:143`)
возвращает `None`, если ключ самодельный. Иначе пользователь увидел бы в поле «УИД»
техническую строку и принял бы её за настоящий сквозной идентификатор.

<a id="11"></a>
## 11. Как определяется case code?

`resolve_case_code` (`app/services/identity.py:35`). Два источника, и первый важнее:

1. **`fetched.case_code` уже заполнен** — номер известен из навигации (таблица результатов
   поиска Москвы). Берём как есть и со страницы **не перечитываем**;
2. иначе достаём из заголовка страницы: `extract_msudrf_case_code`
   (`app/courts/msudrf.py:669`) или `extract_spb_case_code` (`app/courts/spb.py:138`).

Обычные функции, а не методы клиента: номер дела — содержимое **страницы**, а клиент
отвечает за то, как до страницы добраться.

Одна функция на **обе** вёрстки движка, а не по одной на парсер: заголовок с номером у B
и C общий. Если когда-нибудь появится вёрстка, где номер лежит иначе, здесь добавится
понятная ветка с fallback — а не второй парсер-извлекатель.

Номер входит в ключ карточки, поэтому без него дело не сохранить: отсутствие заголовка
означает, что открылась не карточка, и повторять поход бессмысленно (`CaseNotFound`).

<a id="12"></a>
## 12. Как определяется page layout?

`detect_page_type(html)` — `app/parsers/msudrf_shared.py:164`. Смотрит два CSS-селектора:

```python
_TYPE_C_LABELS = "div#contentt td > b"
_TYPE_B_LABELS = "div#contentt td:not([colspan]) > h2"
```

Возвращает `"B"`, `"C"` или `None` («это не карточка»).

Две тонкости, которые легко сломать:

* **C проверяется первым.** На C-страницах тоже есть `<h2>` — это секционные заголовки, и
  без проверки C первым такая страница читалась бы как B;
* охранник `:not([colspan])` не даёт секционным заголовкам сойти за метки.

Определяется вёрстка только у msudrf — у Москвы и Петербурга она одна на портал, и
спрашивать страницу не о чем.

<a id="13"></a>
## 13. Как выбирается Parser?

`get_parser(portal, html)` — `app/parsers/__init__.py:40`. Обычная функция с обычными
`if`, без реестра и без фабрики:

```python
if portal == "mos-sud":
    return MoscowTypeAParser()
if portal == "spb":
    return SpbTypeDParser()
if portal == "msudrf":
    page_type = detect_page_type(html)
    if page_type == "B":
        return MsudrfTypeBParser()
    if page_type == "C":
        return MsudrfTypeCParser()
    raise UnsupportedPage(...)
raise UnsupportedPage(...)
```

Почему нужен И портал, И разметка: у Москвы и Петербурга вёрстка одна на портал, у msudrf
их две и решает страница. `html` — обязательный аргумент, хотя двум порталам из трёх он не
нужен: иначе вызывающий должен был бы помнить, кому его передавать, а кому нет.

Четыре вёрстки:

| Тип | Портал | Отличительная примета |
|---|---|---|
| A | mos-sud.ru | `div.detail-cart`, метки в `div.row_card` |
| B | msudrf.ru, вёрстка 1 | метки в `<h2>`, у таблиц есть `<thead>` |
| C | msudrf.ru, вёрстка 2 | метки в `<b>`, `<thead>` нет, таблица сторон транспонирована |
| D | mirsud.spb.ru | печатная форма `div.case-print` |

**Отличие от старого core:** неопознанная вёрстка msudrf теперь даёт `UnsupportedPage`
сразу. Раньше клиент нёс ожидаемую вёрстку константой класса, страница разбиралась
ожидаемым парсером, разбор выходил пустым, и его отсекал охранник пустого разбора. Итог в
обоих случаях — окончательный отказ, но теперь по нему видно, что портал сменил разметку, а
не «дело почему-то пустое».

<a id="14"></a>
## 14. Что возвращает Parser?

`ParsedCase`. Граница парсера — ровно `HTML → ParsedCase`, и ничего больше: ни сети, ни
БД, ни прокси, ни капчи. Парсер не знает, с какого портала пришла страница и как её добыли.

Одно требование, которого нет в подписи, но которое обязаны соблюдать все парсеры:
**на незнакомом или недорендеренном документе `parse` не падает, а возвращает пустой
`ParsedCase`.** Браузер иногда отдаёт `<html><head></head><body></body></html>`.

Проверено на всех 320 сочетаниях парсер×страница —
`tests/test_parsers_golden.py::test_parser_never_raises`.

### Про golden-файлы

Парсеры содержат накопленное знание о реальных судебных сайтах: терпимость к латинским
двойникам в русских метках (портал отдаёт `Cудья` с латинской `C`), поиск колонок по тексту
шапки вместо номера, порядок проверки меток, обход скрытых мобильных клонов таблиц. Ни одно
из этих правил не выводится из общих соображений — каждое появилось из-за конкретной
страницы конкретного суда.

Поэтому в `tests/golden/` лежат снимки вывода **старых** парсеров по всем 80 сохранённым
страницам, снятые до переноса. `tests/test_parsers_golden.py` прогоняет по тем же
страницам новые и требует совпадения. **Расхождение с golden — это найденная регрессия, а
не повод пересобрать файл.**

<a id="15"></a>
## 15. Что такое ParsedCase?

`app/parsers/parsed_case.py`. Типизированный результат разбора: 12 скалярных полей
карточки плюс шесть списков (судьи, стороны, события, местонахождения, заседания,
документы).

### Главное, что нужно понять: `UNSET`

У скалярных полей **три** состояния, а не два, и разница между вторым и третьим — самое
неочевидное место всего парсинга:

```
поле = "02-0123/2026"   на странице есть метка, вот её значение
поле = None             метка на странице ПРОПАЛА → колонку в БД надо обнулить
поле = UNSET            у этого портала такой метки не бывает ВООБЩЕ → колонку не трогать
```

Наборы меток у порталов разные: Москва отдаёт 11 скалярных полей, msudrf — 6,
Петербург — 4. Если бы отсутствующие поля приезжали как `None`, то при каждом обходе
петербургского дела обнулялись бы «Номер заявления» и «Дата регистрации» — просто потому,
что на этом портале таких меток нет.

Поэтому каждый парсер выставляет **только свои** поля, а остальные остаются `UNSET`.
Собирает их для записи метод `card_fields()`: он отдаёт ровно те, что парсер реально
прислал.

У списков такой проблемы нет: пустой список и есть «на странице ничего не нашлось».

`is_empty()` — охранник перед записью. Пустой разбор **не сохраняется**: страница
считается источником истины, поэтому у уже существующей карточки такой разбор удалил бы
все события и отвязал судей со сторонами. Смена разметки на портале молча вымела бы
историю дела.

<a id="16"></a>
## 16. Где начинается CaseSync?

`sync_case` — `app/services/case_sync.py:114`.

```python
sync_case(session, uid, parsed, court, code, source_url=None) -> CaseChanges
```

Это **единственная** операция, которая приводит БД к состоянию страницы суда. Отдельного
«refresh» рядом с «sync» здесь нет и быть не должно.

Суд, номер дела и адрес приходят **аргументами**, а не внутри `parsed`, и это не
случайность: ни одно из трёх не является содержимым карточки. Суд определяется по
справочнику, номер — из таблицы результатов, адрес знает тот, кто ходил на портал.

Семь шагов, **порядок значим** (тот же порядок повторяет `changes_to_events`):

1. карточка: найти по тройке «УИД + суд + номер» или создать, обновить поля;
2. судьи — полная сверка со страницей;
3. стороны — полная сверка;
4. события «Истории состояний»;
5. история местонахождения;
6. судебные заседания;
7. документы.

Коммит — забота вызывающего. Транзакцией управляет только `session_scope`
(`app/database.py`).

### Два входа, один путь

`app/services/discovery.py`:

```
discover_case(uid=...)         дело неизвестно, пришло УИД      (портал с поиском)
discover_case(source_url=...)  дело неизвестно, пришло ссылкой  (портал без поиска)
resync_case(case_id)           дело известно, берём его источник
```

Все три идут одной дорогой до одного и того же `sync_case`. Различаются они ровно тем,
**откуда взялся** адрес или УИД.

Ни Celery, ни `SearchTask` внутри нет: обход падает исключением, а решать, повторять ли
поход, — дело входной точки.

<a id="17"></a>
## 17. Как работает new / updated / removed?

Одинаково у всех четырёх видов дочерних строк. Возьмём события
(`app/repositories/events.py:50`):

**Проход 1** — по строкам со страницы. Для каждой считается детерминированный `uid`; если
такой строки в базе нет — создаём (`new`), если есть и изменяемое поле отличается —
обновляем (`updated`).

**Проход 2** — всё, чего на странице не оказалось, удаляется (`removed`).

Страница — источник истины: чего там нет, того нет и у нас.

Изменяемые поля у каждой сущности свои, и это не произвол:

| Сущность | Что может измениться |
|---|---|
| поля дела | 11 полей из `_UPDATABLE_FIELDS` (`app/repositories/cases.py`) |
| событие | `event_date` (время может дозаполниться позже), `document_str`, `published_at` |
| местонахождение | только `comment` |
| заседание | `place`, `result`, `basis` |
| документ | **ничего** — ветки `updated` у него нет вовсе |

У документа изменяемых полей не осталось: дата и вид входят в identity, а текст мы не
храним.

Есть охранник, который легко счесть лишним: `if uid in desired_uids: continue` во всех
четырёх синкерах. Портал отдаёт дубли строк, и повторная вставка того же `uid` уронила бы
UNIQUE-индекс **вместе со всей транзакцией дела**.

**Поля дела — отдельная тонкость.** `upsert_by_uid_court_code`
(`app/repositories/cases.py:197`) обновляет только то, что реально пришло:

```python
for field in _UPDATABLE_FIELDS:
    if field not in card_fields:
        continue
```

Это вторая половина истории про `UNSET` из вопроса 15. Отбор делает
`ParsedCase.card_fields()`, сюда приходит уже готовый словарь.

В `_UPDATABLE_FIELDS` намеренно **нет** `url` и `code`. Адресов у карточки несколько, они
лежат в `CaseUrl`. А номер дела входит в ключ карточки: изменение номера означает ДРУГУЮ
карточку, а не изменение этой. Верните `code` в этот список — и обход начнёт переименовывать
существующие карточки вместо того, чтобы заводить новые.

<a id="18"></a>
## 18. Где находятся identity rules?

Разложены по трём местам, и каждое — про свой уровень.

**Ключ карточки** — `Case.card_key` (`app/models/case.py:158`):

```python
f"{self.uid}|{self.court.code}|{self.code}"
```

Единица учёта — не «дело вообще», а его КАРТОЧКА. Суд в ключе потому, что УИД сквозной и
не меняется, когда дело идёт по инстанциям. Номер — потому что по одному УИД в одном суде
бывает несколько производств: приказное, его отмена, затем исковое.

**Уникальность карточки в БД** — `UniqueConstraint("uid", "court_id", "code")`.

**Дочерние строки** — четыре `uuid5`-namespace, по одному на сущность:

| Сущность | Ключ | Файл |
|---|---|---|
| событие | `card_key \| дата \| описание` — **только дата** | `app/repositories/events.py:16` |
| местонахождение | `card_key \| дата \| описание` | `app/repositories/place_history.py` |
| заседание | `card_key \| дата со временем \| стадия` | `app/repositories/court_sessions.py` |
| документ | `card_key \| дата \| вид \| номер повторения` | `app/repositories/documents.py` |

Два места, где легко всё сломать:

**Событие против заседания.** У события в ключ входит только `.date()`, у заседания — дата
со временем. Поэтому дозаполнение времени у события даёт UPDATE той же строки, а у
заседания — новую строку. Так и задумано: перенос заседания это новое заседание, а
уточнение времени события — то же событие.

**Номер повторения у документа.** `occurrence` — это счётчик одинаковых `(дата, вид)`,
встретившихся **выше на той же странице**. Портал отдаёт до 21 одинаковой строки
«Приложение» за одну дату, и различает их только позиция. Отсюда следствие:
**порядок строк, который отдал парсер, пересортировывать нельзя** — иначе `uid` разъедутся
и получится волна ложных удалений и вставок.

**Адрес карточки** — `canonical_case_url` (`app/validators.py:60`). Приводит схему к
`https`, хост к нижнему регистру, снимает завершающий слэш и **сортирует значимые
query-параметры**. Каждое из этих действий входит в ключ уникальности `CaseUrl.url` и в
`synthetic_uid`, поэтому менять канонизацию нельзя: поедут самодельные ключи, а с ними
`card_key` и все дочерние `uid`.

Все правила прибиты к литеральным значениям в `tests/test_identity.py` — там нет ни одного
вычисляемого ожидания. Если считать ожидание той же функцией, которую проверяешь, тест
переживёт любое изменение формулы и не поймает ничего.

<a id="19"></a>
## 19. Где происходит timezone conversion?

Ровно в двух местах, оба — на границе БД:

* `app/repositories/events.py:76` — `event_at = to_utc(local_at, court_tz)`
* `app/repositories/court_sessions.py:78` — то же для заседания

Правила:

* **парсеры отдают наивное локальное время** — портал пишет своим местным и пояса не
  указывает. Aware-значение отдавать нельзя: парсер про суд ничего не знает;
* **пояс берётся у суда** — `Court.timezone`, IANA-имя вроде `Europe/Moscow`. Именно имя,
  а не смещение: смещения меняются решениями законодателя, а имя зоны переживает такой
  перенос. Вычисляется из региона и кода — `timezone_for` (`app/timezones.py:151`);
* **календарные даты остаются `date`** — дата поступления дела, дата документа. У них нет
  времени, и приписывать им полночь значит выдумывать момент, которого не было;
* **`timezone_for` намеренно падает** на неизвестном регионе, а не подставляет Москву:
  молчаливый дефолт означал бы тихо неверные моменты у дел целого региона.

### Асимметрия, которую нельзя нарушить

**Хранение — в UTC. Identity — по ЛОКАЛЬНОМУ времени.**

```python
event_at = to_utc(local_at, court_tz)              # в колонку — UTC
uid = event_uid(case.card_key, local_at, ...)      # в ключ — локальное
```

Это выглядит как ошибка, но так и задумано. Хешируй мы UTC — одинаковое настенное время в
разных зонах давало бы разные ключи, а переход на `timestamptz` переписал бы все
сохранённые `uid`.

Отсутствующее время → **локальная полночь, детерминированно**. Не `None`: время участвует
в identity заседания, и недетерминированный fallback переписывал бы `uid` на каждом
разборе.

<a id="20"></a>
## 20. Что такое CaseChanges?

`app/services/case_sync.py:47`. Результат одной сверки: что появилось, что изменилось,
что пропало.

18 полей: сама карточка, признак `is_new`, изменения скалярных полей и по три списка
(`new` / `updated` / `removed`) на каждый вид дочерних строк — кроме документов, у которых
только `new` и `removed`, и кроме судей со сторонами, у которых `added` / `removed`.

`has_changes()` отвечает, было ли вообще что-нибудь.

Кому это нужно:

* `app/outbox.py` раскладывает `CaseChanges` в поток событий;
* `_log_changes` (`app/services/discovery.py:405`) пишет изменения в лог человеческим
  текстом;
* `mark_checked` по `has_changes()` решает, обновлять ли `last_changed_at`.

`is_new` заслуживает отдельного внимания: у новой карточки список изменений полей **всегда
пуст**. Появление дела — само по себе событие, и засорять diff переходами `None → значение`
по каждому полю незачем. На этом же признаке стоит подавление baseline в outbox.

<a id="21"></a>
## 21. Зачем существует OutboxEvent?

Чтобы можно было дёшево ответить на вопрос **«что изменилось по делу после такого-то
момента»**.

Раньше весь diff уходил одним куском в JSONB-колонку `Case.diff_history`: оттуда такое не
выбрать, а строка дела переписывалась на каждом обходе. Теперь каждое атомарное изменение —
отдельная строка `outbox_event` со своим типом и компактным payload.

Раскладка — `changes_to_events` (`app/outbox.py:126`), запись — `OutboxEventRepository.emit`
(`app/repositories/outbox_events.py:21`), чтение — `GET /cases/{id}/events`.

### Главное свойство: атомарность

`emit` вызывается **в той же транзакции**, что и само изменение карточки —
`app/services/discovery.py`, внутри `session_scope` рядом с `sync_case`. Отсюда два
следствия, ради которых всё и сделано:

* событие не может **потеряться** — оно коммитится вместе с изменением;
* событие не может **появиться без изменения** — откат уносит и то и другое.

Есть и техническая причина звать `changes_to_events` до коммита: у удалённых событий и
местонахождений атрибуты в этот момент ещё загружены в сессию, а после коммита читать их
было бы уже нечем.

Закреплено тестом `tests/test_outbox.py::test_rollback_leaves_no_events`.

### Baseline

**Первый обход дела событий НЕ создаёт** — `if changes.is_new: return []`.

Вся карточка на нём формально «новая»: десятки строк истории состояний, заседания,
документы. Но это не изменения — так на портале было и до нас. Выпустить по ним события
значило бы сказать «вот что поменялось» про то, что не менялось.

Практическое следствие для интерфейса: у только что добавленного дела экран «что нового»
будет пуст, и это правильное состояние, а не ошибка загрузки.

<a id="22"></a>
## 22. Почему OutboxEvent не является notification?

Потому что core не знает получателей. Ни пользователей, ни подписок, ни каналов, ни того,
что считать поводом написать.

Строка `outbox_event` означает ровно одно: **«core обнаружил, что на портале это
изменилось»**. Не «надо кому-то отправить».

Поэтому в модели и в payload **нет и не должно быть** ни `user_id`, ни `sent`, ни
`delivered`, ни `notification_status`, ни email, ни Telegram ID. Проверяется тестом
`tests/test_outbox.py::test_payload_has_no_delivery_fields`.

Есть и практическая причина, помимо границы ответственности: на одно дело может быть
подписано несколько пользователей, и пометка «отправлено» на самой строке потеряла бы
событие для всех, кроме первого. Таблица append-only: строки только добавляются, никогда
не редактируются.

Единственное состояние доставки, которое core вообще знает, — «ушло ли сообщение в
брокер», — живёт в ОТДЕЛЬНОЙ таблице `integration_outbox_event` (вопрос [26](#26)). Оно
про брокер, а не про пользователя, и здесь ему всё равно не место.

<a id="23"></a>
## 23. Почему Outbox читается по `id`?

**Он читается не по `id`, а по `created_at`** — и об этом стоит знать честно, потому что
ТЗ просило иначе.

`OutboxEventRepository.list_since` (`app/repositories/outbox_events.py:44`) отбирает
события строгим `created_at > since` и сортирует по `(created_at, id)`. Переход на курсор
по `id` был сделан и затем **отменён решением заказчика**.

Что из этого следует практически:

* `created_at` берётся из `func.now()`, то есть из момента **начала транзакции**. У всех
  событий одного обхода метка **одинаковая**;
* поэтому взаимный порядок событий внутри одного обхода держится только вторичной
  сортировкой по `id` в `ORDER BY` — она на месте и покрыта тестом
  `tests/test_outbox.py::test_events_are_read_in_the_order_they_were_found`;
* сравнение строгое (`>`), а не нестрогое. Выбор между двумя неприятностями: строгое
  теряет события с той же меткой, что у последнего показанного, нестрогое отдаёт уже
  показанные повторно. Выбрано первое.

У курсора по `id` этой дилеммы не было бы: `id` строго возрастает, уникален и не зависит от
часов. Если однажды решите вернуться к нему — менять надо `list_since`, составной индекс
`ix_outbox_event_case_created` и параметр `since` у роута.

Расхождение зафиксировано в `services/core_v2_AUDIT.md`, пункт 54.

<a id="24"></a>
## 24. Как устроен регулярный обход дел?

Три шага, и первый из них происходит не в core.

```
клиентский сервис                    core
какие дела интересны   ──PUT──▶   как и когда их обновлять
```

**1. Клиент говорит, за какими делами следят.** `PUT /monitoring/cases`
(`app/api/monitoring.py`) принимает полный список id: «после этого запроса на мониторинге
ровно эти дела». Ручка выставляет `Case.is_on_monitoring` — единственное поле карточки,
которым распоряжается не core.

Список ПОЛНЫЙ, а не дифф, и это главное решение здесь. Клиент знает своё состояние
целиком и не знает нашего: дифф ему считать нечем, а разошедшиеся состояния он бы уже не
свёл. Замещение же идемпотентно — повторный запрос с тем же списком меняет 0 строк
(`CaseRepository.set_monitoring_list`) — и сходится с любого расхождения за один вызов.

Пустой список отклоняется с 409, если не передан `?force=true`. Пустое тело — законное
состояние («ни на что больше не подписаны»), но оно же самая вероятная форма аварии на
стороне клиента, и в запросе одно от другого не отличить. Цена ошибки несимметрична:
лишний обход стоит одного похода на портал, а снятое зря дело перестаёт обновляться
МОЛЧА, и никто этого не замечает, пока пользователь не спросит, почему по делу третью
неделю ничего нет.

**2. Раз в сутки планировщик набирает помеченные дела.** `app/tasks.py`,
`sync_monitored_cases` — задача под `beat_schedule` (`app/celery_app.py`). Она только
ВЫБИРАЕТ дела и кладёт их в `regular`; сам обход — существующий `enqueue_case_resync`, тот
же, которым идёт ручной прогон из админки и запрос пользователя. Своей логики
синхронизации для мониторинга нет и быть не должно: обход дела не зависит от того, почему
за ним пошли.

**3. Дела разносятся по времени.** `countdown = позиция * MONITORING_SPACING_SECONDS`.
Не оптимизация, а условие работы: один поход — 25-35 секунд браузера, аренда прокси из
ограниченного пула и ОПЛАЧЕННАЯ капча. Поставь тысячу дел одновременно — воркеры разберут
очередь вперегонки, прокси кончатся, и деньги за капчу уйдут на попытки, которые упадут по
таймауту.

Выборка (`CaseRepository.list_monitored_ids`) сортируется по `last_checked_at` с NULLS
FIRST, а не по id. Это страховка от `MONITORING_BATCH_LIMIT`: с сортировкой по id
урезанная выборка брала бы одни и те же первые N каждые сутки, а хвост списка не обошёлся
бы никогда. Так же устроен и частичный индекс `ix_case_on_monitoring` — он закрывает этот
запрос целиком.

### Флаг на карточке, а не на подписке

`is_on_monitoring` — свойство ДЕЛА, и это не экономия на схеме. Если на дело подписаны
Наташа, Аня и Пётр, мы всё равно идём на портал один раз: поход стоит прокси и капчи, и он
не должен множиться на число заинтересованных. Клиент это знает и присылает
distinct-список; core же устроен так, что даже присланный трижды id даст одно дело
(`test_duplicates_in_the_list_are_collapsed`).

Отсюда же следует, чего в core нет: ни пользователей, ни подписок, ни интервала обхода на
пользователя. Появись здесь настройка вида `MONITORING_INTERVAL` на подписчика — значит,
знание о подписках просочилось внутрь, и обратно его уже не вынуть. Проверяется тестами
`test_core_knows_nothing_about_users` и `test_monitoring_settings_are_about_timing_only`.

### Чем это отличается от мониторинга в старом core

Именами и владельцем флага, а не механикой. В старом core флаг звался
`monitoring_enabled`, и ставил его сам core (`POST /cases/{id}/monitoring`, тумблер на
дело). Тумблер невозможно свести с состоянием клиента: два потерянных запроса, и списки
разошлись навсегда. Поэтому осталась одна ручка, и она замещающая.

Заодно при переписывании ушёл мёртвый код, к мониторингу отношения не имевший: таблицы
`instance` и `case_link` (их не заполнял ни парсер, ни задача), колонка `document_text`
(была помечена «намеренно не заполняется»), внешний ключ `event.document_id` (его никто не
выставлял).

### Что здесь НЕ мониторинг

`last_checked_at` и `last_changed_at` — факты о деле, а не служебные поля планировщика:
«когда мы последний раз смотрели страницу» и «когда на ней последний раз что-то менялось».
Показывать надо ОБЕ и рядом: «дело не менялось три месяца» и «дело три месяца не
проверяли» — разные вещи, и вторая означает, что что-то сломалось.

`updated_at` на роль «даты обновления дела» **не годится**: строку трогает любой обход, в
том числе холостой.

`resync_case` (`app/services/discovery.py:209`) и `enqueue_case_resync`
(`app/tasks.py:133`) — обычная операция «сходи по этому делу сейчас». Планировщик её
ЗОВЁТ, но ею не является: ручной прогон из админки идёт тем же путём.

<a id="25"></a>
## 25. Как клиентский сервис взаимодействует с Core?

Только по HTTP (и, начиная с публикации outbox, через RabbitMQ). Ни общей БД, ни общей
ORM, ни общих моделей — и это не вкусовщина: две ORM на одних таблицах ломаются на каждой
миграции.

```
клиентский Django
├── пользователи
├── аутентификация
├── UI
├── подписки
├── unread
└── доставка уведомлений
              │
      HTTP API ↓        ↑ RabbitMQ (case_changes)
              │
core_v2
├── суды
├── дела
├── поход на портал
├── разбор
├── синхронизация
├── регулярный обход
└── события об изменениях
```

**Django не должен знать, как устроены сайты судов. Core не должен знать, как устроены
пользователи.**

Что core предоставляет:

| Метод | Путь | Для чего |
|---|---|---|
| `POST` | `/search_case` | добавить дело: принять ссылку или УИД, завести задачу |
| `GET` | `/search_case/tasks/{id}` | статус задачи — опрашивают, пока дело ищется |
| `GET` | `/cases?ids=1,2,3` | витрины нескольких дел одним запросом — страница «мои дела» |
| `GET` | `/cases/{id}` | полная карточка со всеми вложенными сущностями |
| `GET` | `/cases/{id}/summary` | лёгкая витрина одного дела |
| `GET` | `/cases/{id}/events` | что изменилось по делу после указанного момента |
| `PUT` | `/monitoring/cases` | какие дела держать на регулярном обходе |

Схема на стороне клиента (`services/client`):

```
User → CaseSubscription   → core_case_id
     → PendingCaseSearch  → core_task_id   (ждём ответа по ссылке)
     → UserCaseChange      (unread, Phase 6)
```

Клиент хранит, кто на что подписан и что кому уже показано, а судебные данные для
отображения забирает через API и НЕ копирует себе. Список дел на мониторинге он
пересобирает из своих подписок с `distinct` и отправляет одним `PUT`.

`GET /cases?ids=` появилась именно под страницу «мои дела»: без неё клиент собирал бы её
из N последовательных вызовов `/cases/{id}/summary`, то есть N+1, только по сети, где
каждый шаг стоит десятки миллисекунд.

**Чего сейчас нет и что понадобится добавить под реальный запрос:** эндпоинта постановки
дела на повторный обход по HTTP (сейчас `enqueue_case_resync` зовётся из кода, из админки
и из планировщика) и чтения событий сразу по нескольким делам.

**Аутентификации на API нет.** Наружу публикуется только клиентский сервис (порт 8001),
core живёт внутри сети. Знать об этом надо: `PUT /monitoring/cases` меняет состав обхода всех дел, и
единственная его защита сейчас — сетевая изоляция.

<a id="26"></a>
## 26. Что такое DomainEvent и IntegrationEvent и зачем их два?

Три разных понятия, которые легко спутать, потому что все три зовут «событием».

| Понятие | Что это | Где живёт |
|---|---|---|
| `Event` | **судебный факт** со страницы: «23.08.2026 — назначено судебное заседание» | таблица `event` |
| `DomainEvent` | **факт внутри core**: «по делу 481 появилось событие» | обычный dataclass, `app/outbox.py` |
| `IntegrationEvent` | **публичный контракт**: то же, но в виде, обещанном наружу | `app/integration_events.py` |

Путь такой:

```
CaseChanges
    │ changes_to_events()          app/outbox.py
    ▼
DomainEvent(event_type, payload, entity)
    │
    ├──▶ OutboxEventRepository.emit()      ──▶  outbox_event
    │    домен-лог: богатый payload,            читается по HTTP,
    │    append-only                            курсор по created_at
    │
    └──▶ to_integration_events()           ──▶  integration_outbox_event
         app/integration_events.py               скудный контракт,
                                                 published_at, едет в RabbitMQ
```

Обе записи — в ОДНОЙ транзакции с изменением карточки (`app/services/discovery.py`).

### Почему DomainEvent нельзя отдать наружу как есть

Потому что он меняется вместе со сверкой, а клиентский сервис от этого ломаться не должен.
Появится у заседаний новое изменяемое поле — поменяется `payload`; разъедутся ветки
`updated` — поменяется набор типов. Это правки внутри core, и деплоя клиента они требовать
не должны.

Сейчас публичное имя типа буква в букву совпадает с внутренним (`event_new` и там и там), и
соблазн сэкономить очень велик. Именно поэтому соответствие задано ЯВНОЙ таблицей
`INTEGRATION_TYPE_BY_DOMAIN`: пока она есть, внутреннее имя можно переименовать, и наружу
это не просочится. Её полноту проверяет тест — забыть новый тип молча не получится.

По той же причине `integration_outbox_event.event_type` — строка, а не `Enum`: `Enum` в БД
означал бы, что переименование внутреннего типа требует миграции публичной таблицы.

### Почему две таблицы, а не published_at в outbox_event

У них разные работы, и склеивать их значит связать публичный контракт с внутренним
устройством:

* `outbox_event` — append-only домен-лог с богатым payload. Инвариант «строки не
  редактируются» заявлен и держится (вопрос [22](#22));
* `integration_outbox_event` — очередь на публикацию. `UPDATE` ей нужен по определению:
  `published_at` для этого и существует.

Цена решения — дублирование строк. Платим байтами: публичная строка это тип, два id,
версия и момент, без payload вовсе.

### Схема — это и есть контракт

Колонки `integration_outbox_event` ровно те, что уезжают в JSON, поэтому JSONB-колонки
там нет:

```json
{"id": 1502, "type": "event_new", "version": 1,
 "case_id": 481, "entity_id": 712, "occurred_at": "2026-08-23T13:20:00Z"}
```

Добавить поле в сообщение нельзя, не добавив его в схему, — и наоборот. JSONB позволил бы
менять формат молча, то есть ровно то, от чего вторая таблица и защищает.

`id` сообщения — идентификатор для идемпотентности на стороне клиента: доставка
**at-least-once**, и повторно пришедшее сообщение он обязан отбросить по этому id.

### Ловушка: entity_id и порядок вызовов

`DomainEvent` несёт ССЫЛКУ на изменившуюся строку (`entity`), а не её id. Причина
механическая: у только что созданных `Event`/`CourtSession`/`Document` id появляется
только при `flush`, а `DomainEvent` собирается до него.

Флашит `OutboxEventRepository.emit`. Значит, `to_integration_events` надо звать ПОСЛЕ
него — так и сделано в `discovery.py`. Перепутать порядок легко, а ошибка тихая: исключения
не будет, просто у всех новых сообщений `entity_id` окажется пустым, и клиент сможет
сказать только «в деле что-то поменялось» вместо «вот ЭТО новое». Покрыто тестом
`test_change_found_on_re_crawl_is_queued_for_publishing`, который гоняет настоящий обход.

У пропавших со страницы строк (`*_removed`) id читается нормально: сессия живёт с
`expire_on_commit=False`.

### Публикуются все 16 типов

Фильтра в core нет. Что из изменений достойно показа пользователю и что из них повод
написать письмо — решает клиентский сервис: он знает подписки, интерфейс и настройки
уведомлений. Фильтр здесь означал бы, что новый тип в UI требует деплоя core.

### Очередь `case_changes` — не Celery

Там обычный JSON. `urgent` и `regular` значат «выполни работу», а `case_changes` —
«работа уже произошла, вот факт изменения». Смешивать их нельзя.

Как сообщения попадают в эту очередь — вопрос [27](#27).

<a id="27"></a>
## 27. Как изменения уезжают в RabbitMQ?

Отдельный процесс, `python -m app.integration_publisher` (контейнер
`core-v2-outbox-publisher`). Цикл простой до скуки:

```
take_unpublished(100)  →  опубликовать каждое  →  published_at = now()  →  коммит
     FOR UPDATE                                                              │
     SKIP LOCKED                                                             │
                          пусто или порция неполная? спать PUBLISHER_POLL_SECONDS
```

Топология: durable exchange `soroka.case_changes` (direct) + durable очередь
`case_changes`, привязанная к нему. Сообщения persistent (`delivery_mode=2`).

Всё три durable/persistent вместе, потому что порознь они не значат ничего: перезапуск
брокера иначе стёр бы накопленное, а в `integration_outbox_event` эти сообщения уже
помечены опубликованными — то есть изменения пропали бы навсегда и молча.

Exchange, а не публикация в очередь напрямую: завтра к тому же потоку захочется привязать
вторую очередь (Telegram-бот, аналитика), и с exchange это одна строка на стороне
подписчика, а не переделка publisher'а.

### Почему отдельный процесс

Чтобы обход не зависел от брокера. Публиковать прямо в транзакции сверки — значит связать
сохранение судебных данных с доступностью RabbitMQ: упал брокер, и дело, за которым мы
честно сходили на портал (прокси, капча, тридцать секунд), не сохранится. Transactional
Outbox ровно эту связь и разрывает.

Не Celery-задача, потому что задача нужна, когда работу надо *запланировать*, а здесь она
есть всегда. Задача раз в секунду означала бы секундный поток мусора в очереди задач.

Опрос, а не `LISTEN/NOTIFY`: секунда задержки на пути, где сам обход занимает 25-35 секунд,
не значит ничего, а опрос по частичному индексу `ix_integration_outbox_unpublished` по
пустой таблице стоит примерно ничего.

### Порядок операций: сначала публикуем, потом отмечаем

Обратный интуитивному, и выбран сознательно. Отметив до публикации, при падении мы бы
сообщение **потеряли**; так — в худшем случае отправим дважды. Из двух неприятностей
выбрана обратимая: дубль читающий отбросит по id, а потерю не восстановит никто.

Отсюда **at-least-once**, и это не недоделка. Публикация в брокер и `UPDATE published_at` —
две операции в двух системах, между ними процесс может умереть.

### Частичный успех

Порция, упавшая на пятидесятом сообщении, обязана оставить помеченными первые сорок девять.
Поэтому `publish_batch` ошибку **возвращает** (в `Batch.error`), а не бросает: брошенное
исключение заставило бы `session_scope` откатить транзакцию вместе с этими отметками, и все
сорок девять уехали бы повторно.

Покрыто тестом `test_failed_publish_keeps_the_prefix_marked` — свойство из тех, что легко
потерять рефакторингом «уберём странный возврат ошибки».

### Остановка по сигналу

`docker compose stop` присылает SIGTERM. Без обработчика процесс умер бы посреди порции:
часть сообщений в брокере, отметки не закоммичены — после перезапуска дубли. Обработчик
доводит текущую порцию и выходит.

### Ровно одна реплика

Больше не нужно: секундного опроса хватает с запасом. Больше и не сломает — порция берётся
через `FOR UPDATE SKIP LOCKED`, поэтому второй publisher возьмёт следующие строки, а не те
же. Защита стоит дёшево, а цена ошибки — дубли у каждого подписчика.

### Очередь `case_changes` — не Celery

Там обычный JSON, а не celery-протокол. `urgent` и `regular` значат «выполни работу»,
`case_changes` — «работа уже произошла, вот факт изменения». Смешивать нельзя: подписчик
второй очереди — чужой сервис, и celery-протокол ему разбирать нечем.

Подписчик — `manage.py consume_case_events` в `services/client`. Он объявляет тот же
exchange и ту же очередь с теми же параметрами, поэтому порядок запуска контейнеров не
важен. Одна тонкость на стыке: адрес брокера в `.env` записан в форме `amqp://…:5672//`,
которую kombu читает как vhost `/`, а pika — как ПУСТОЙ vhost. Клиент приводит её сам;
подробности — в `services/client/README.md`.

### Как проверить руками

```bash
docker compose up -d core-v2-outbox-publisher
docker compose logs -f core-v2-outbox-publisher
docker compose exec rabbitmq rabbitmqctl list_queues name messages
```

Сообщения видно и в Management UI: http://localhost:15672, очередь `case_changes`.

## Куда смотреть, если что-то пошло не так

| Симптом | Где искать |
|---|---|
| Дело не заводится, «суда нет в справочнике» | не залит `data/courts.json` → `python scripts/sync_courts.py` |
| Задача висит в `RUNNING` | воркер умер жёстко. Терминальный статус ставится только явными вызовами; такая задача блокирует повторный запрос этого УИД через API |
| «Не удалось разобрать страницу» | портал сменил вёрстку. Включите `HTML_SNAPSHOT_ENABLED=1`, повторите обход, посмотрите снимок в S3 |
| Разбор пустой, карточка не сохранилась | тот же случай: охранник `is_empty()` не дал затереть существующие события |
| Задача падает на прокси | пустой пул при `COURT_PROXY_REQUIRED=1`. Заведите прокси через `/admin` или `scripts/check_proxy.py` |
| События не приходят по свежему делу | так и должно быть: первый обход — baseline (вопрос 21) |
| Дело на мониторинге, а не обходится | не поднят `core-v2-beat`, либо `MONITORING_BATCH_LIMIT` меньше числа дел |
| Сообщения копятся с пустым `published_at` | не поднят `core-v2-outbox-publisher`, либо он не может достучаться до брокера. Core изменения находит, клиент о них не узнаёт |
| У сообщений пустой `entity_id` | `to_integration_events` позвали ДО `OutboxEventRepository.emit` — id появляется только после его flush (вопрос 26) |
| Дела молча снялись с мониторинга | клиент прислал неполный список в `PUT /monitoring/cases`. Пустой отклоняется с 409, а вот укороченный — нет |
| Тесты падают с `Connection refused` | не поднят PostgreSQL. Без базы: `pytest -m "not db"` |
| Клиент получил одно изменение дважды | так и задумано: доставка at-least-once. Отбрасывать дубли по `id` сообщения — забота читающего (вопрос 27) |

## Правила, которые стоит запомнить

1. **Клиент — на способ доступа, парсер — на вёрстку.** Новая вёрстка добавляет парсер, а
   не клиента.
2. **Суд — только по справочнику.** Никогда из УИД.
3. **Ключ карточки не меняется.** Ни при появлении настоящего УИД, ни при чём ещё.
4. **`UNSET` ≠ `None`.** Первое — «такого поля у портала не бывает», второе — «метка
   пропала со страницы».
5. **Порядок строк документов не пересортировывать.** Он входит в identity.
6. **Identity по локальному времени, хранение в UTC.** Не «исправляйте».
7. **Никакого `async def` на пути до похода в суд.**
8. **Пустой разбор не сохранять.**
9. **События пишутся в той же транзакции, что и изменение.**
10. **Какие дела обходить — знание клиента, когда обходить — решение core.**
    Пользователей и подписок в core нет.
11. **Сначала опубликовать, потом отметить published_at.** Наоборот — потеря
    сообщения; так — в худшем случае дубль, а его читающий отбросит по id.
12. **Golden-файлы не пересобирать**, пока не доказано, что изменение поведения намеренное.
