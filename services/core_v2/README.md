# Soroka Core v2

Backend, отвечающий за одно: **получить страницу суда → понять, какая это карточка →
разобрать → синхронизировать с БД → зафиксировать обнаруженные изменения.**

Core не знает про пользователей, подписки, тарифы, UI и рассылку уведомлений. Это
граница: пользователями займётся отдельный Django-сервис, который будет обращаться к
core по HTTP.

Старый `services/core` — **reference implementation, только для чтения.** Он не
меняется, и `core_v2` не импортирует из него ни строки кода.

Подробный разбор старого core, вместе со списком рисков переноса, лежит в
`services/core_v2_AUDIT.md`. Полное описание архитектуры появится в `ARCHITECTURE.md`
по завершении переноса.

## Состояние

Перенос завершён (ТЗ §29, все фазы). Готово:

* `app/models/` — 13 моделей в 8 модулях по группам сущностей;
* `app/repositories/` — 10 репозиториев доступа к данным;
* `app/services/case_sync.py` — единственная операция синхронизации;
* `app/parsers/` — 4 парсера вёрстки (A, B, C, D) и типизированный `ParsedCase`;
* `app/courts/` — три клиента судов (Москва, msudrf, Петербург) и выбор клиента;
* `app/browser/`, `app/captcha/`, `app/storage/` — браузер, прокси, капча, S3;
* `app/services/identity.py` — чем опознаём карточку: УИД и номер дела;
* `app/parsers/get_parser` — выбор парсера по порталу и по самой странице;
* `app/services/discovery.py` — `discover_case` и `resync_case`: два входа, один путь;
* `app/outbox.py` — раскладка изменений в поток событий, атомарно со сверкой;
* `app/api/` — HTTP-роуты: запуск обхода, чтение карточки, чтение событий;
* `app/tasks.py` — Celery-задачи, жизненный цикл `SearchTask`, учёт капчи;
* `app/admin.py` — админка на `/admin`;
* `app/validators.py` — правила identity (канонизация адресов, синтетические УИД);
* одна initial-миграция alembic под всю схему.

Работает вся цепочка от HTML до БД:

```
HTML -> парсер -> ParsedCase -> sync_case -> PostgreSQL + CaseChanges
```

Работает вся цепочка целиком: `discover_case(source_url=…)` сходит на портал, определит
суд, УИД и номер дела, выберет парсер по вёрстке и сохранит карточку.

Старый Django-клиент удалён вместе со всей инфраструктурой, существовавшей только ради
него. `docker-compose up` поднимает инфраструктуру и три контейнера core_v2.

Осталось написать `ARCHITECTURE.md` — сквозное описание для того, кто открывает проект
впервые.

Пустых каталогов «на будущее» здесь нет намеренно: папка появляется вместе с кодом,
который в неё ложится.

```
pip install -r requirements.txt

```

## База данных

Своя база — `soroka_core_v2`, отдельная от базы старого core. Причина не в
предпочтениях: `alembic_version` это однострочная таблица, поэтому две независимые
истории миграций в одной базе невозможны. Побочная польза — старый core можно держать
запущенным рядом и сверять поведение.

Заводится скриптом `deploy/postgres/init.sql` при первой инициализации кластера.

```
alembic upgrade head
```

История миграций начинается с нуля: 27 миграций старого core сюда не копируются,
первая ревизия описывает целевое состояние моделей сразу, без monitoring-колонок.

## Про парсеры и golden-файлы

Парсеры содержат накопленное знание о реальных судебных сайтах: терпимость к латинским
двойникам в русских метках («Cудья» с латинской C), поиск колонок по тексту шапки, а не
по номеру, порядок проверки меток, обход скрытых мобильных клонов таблиц. Ни одно из этих
правил не выводится из общих соображений — каждое появилось из-за конкретной страницы
конкретного суда.

Поэтому в `tests/golden/` лежат снимки вывода **старых** парсеров по всем 80 сохранённым
страницам, снятые до переноса, а `tests/test_parsers_golden.py` прогоняет по тем же
страницам новые парсеры и требует совпадения. Расхождение — это найденная регрессия, а не
повод пересобрать golden.

Единственное намеренное расхождение задокументировано в самом тесте, в константе
`PUBLISHED_AT_ADDED_TO_TYPE_A`.

## Клиенты судов: клиент на способ доступа, а не на вёрстку

Три клиента, потому что есть три способа добраться до карточки: форма поиска по УИД
(Москва), прямая ссылка с прохождением капчи (msudrf), прямая ссылка с ожиданием
отрисовки (Петербург). Вёрсток при этом четыре — движок msudrf отдаёт две.

**Новая вёрстка добавляет парсер, а не клиента.** Новый клиент нужен только тогда, когда
меняется сам способ добраться до страницы. В старом core у msudrf было два клиента, и
второй состоял целиком из одной строки `page_type = "C"`.

Прокси клиент не арендует — получает готовый аргументом. Аренда живёт в
`app/services/proxy_pool.py`, потому что открывает сессию БД, а пакет браузера про базу
знать не должен.

## Identity: чем опознаём карточку

Ключ карточки — тройка «УИД + суд + номер дела». От неё считаются детерминированные uid
всех дочерних строк, поэтому сменить ключ существующей карточки значит перестать узнавать
её события и документы.

Три обычные функции в `app/services/identity.py` и `app/courts/base.py`, без классов:
`find_uid`, `resolve_case_code`, `resolve_case_uid`. У последней три шага, и порядок
обязателен: сохранённый УИД карточки важнее найденного на странице. Это единственное, что
делает самодельный ключ (`synthetic_uid`) безопасным — портал может дозаполнить УИД
позже, и подмена ключа устроила бы волну ложных удалений.

## Discovery и re-sync — два входа в один путь

`app/services/discovery.py`:

```
discover_case(uid=...)         дело неизвестно, пришло УИД      (портал с поиском)
discover_case(source_url=...)  дело неизвестно, пришло ссылкой  (портал без поиска)
resync_case(case_id)           дело известно, берём его источник
```

Дальше все три идут одной дорогой до одного и того же `sync_case`. Отдельного «refresh»
рядом с «sync» нет: они различаются ровно тем, откуда взялся адрес или УИД.

Ни Celery, ни `SearchTask` внутри нет. Обход падает исключением, а решать, повторять ли
поход, — дело входной точки; отличить временный отказ от окончательного помогает
`is_terminal(exc)`.

## Outbox: это не уведомления

Строка `outbox_event` означает ровно одно: **core обнаружил, что на портале что-то
изменилось.** Не «надо кому-то отправить»: core не знает ни пользователей, ни подписок,
ни каналов. Поэтому в payload нет и не должно быть ни `user_id`, ни `sent`, ни
`delivered`.

Два свойства, ради которых всё устроено именно так:

* **атомарность** — события пишутся в ТОЙ ЖЕ транзакции, что и изменение карточки
  (`app/services/discovery.py`). Событие не может потеряться и не может появиться без
  изменения; откат уносит оба;
* **baseline** — первый обход событий НЕ создаёт. Вся карточка на нём формально «новая»,
  но это не изменения: так на портале было и до нас.

Читаются события через `GET /cases/{case_id}/events?since=<момент>`. В старом core такого
эндпоинта не было вовсе — события писались, но прочитать их можно было только глазами в
админке.

## Что где лежит

```
HTTP / Celery      app/api/, app/tasks.py, app/admin.py   тонкие входные точки
оркестрация        app/services/discovery.py              два входа, один путь
сверка             app/services/case_sync.py              единственная запись в БД
события            app/outbox.py                          что изменилось
разбор             app/parsers/                           HTML -> ParsedCase
поход на портал    app/courts/, app/browser/, app/captcha/
данные             app/models/, app/repositories/
```

Читать сверху вниз: каждый слой знает только тот, что ниже. Задача не знает, как устроен
портал; обход не знает про Celery и `SearchTask`; парсер не знает, откуда взялась
страница; клиент суда не знает, что с ней будут делать.

## Правило про async

Все роуты FastAPI объявлены обычным `def`, а не `async def`, и так должно остаться.
Походы на порталы судов идут через Playwright **sync** API, а `sync_playwright()`
падает внутри работающего event loop. FastAPI выполняет обычный `def` в отдельном
потоке — там event loop'а нет. Первый же `async def` на пути до похода в суд сломает
это молча и не сразу, поэтому правило закреплено тестом
(`tests/test_skeleton.py::test_all_routes_are_sync`).
