# Soroka Core v2

Backend, отвечающий за одно: **получить страницу суда → понять, какая это карточка →
разобрать → синхронизировать с БД → зафиксировать обнаруженные изменения.**

Core не знает про пользователей, подписки, тарифы, UI и рассылку уведомлений. Это
граница: пользователями занимается отдельный клиентский сервис, который обращается к core
по HTTP.

Единственное, что core узнаёт извне, — **какие дела кому-то интересны**: клиент присылает
полный список запросом `PUT /monitoring/cases`. Что с этим списком делать, core решает сам
(раз в сутки ставит помеченные дела на обычный повторный обход). Коротко:

    клиент: какие дела интересны   →   core: как и когда их обновлять

Старый `services/core` — **reference implementation, только для чтения.** Он не
меняется, и `core_v2` не импортирует из него ни строки кода.

Подробный разбор старого core, вместе со списком рисков переноса, лежит в
`services/core_v2_AUDIT.md`. Сквозное описание архитектуры — в `ARCHITECTURE.md`.

## Состояние

Перенос завершён (ТЗ §29, все фазы). Готово:

* `app/models/` — 13 моделей в 8 модулях по группам сущностей;
* `app/repositories/` — 10 репозиториев доступа к данным;
* `app/services/case_sync.py` — единственная операция синхронизации;
* `app/parsers/` — 4 парсера вёрстки (A, B, C, D) и типизированный `ParsedCase`;
* `app/courts/` — три клиента судов (Москва, msudrf, Петербург) и выбор клиента;
* `app/browser/`, `app/captcha/`, `app/storage/` — браузер, прокси, капча, S3;
* `app/services/identity.py` — чем опознаём карточку: УИД и номер дела;
* `app/parsers/get_parser` — выбор парсера по порталу и по самой странице;
* `app/services/discovery.py` — `discover_case` и `resync_case`: два входа, один путь;
* `app/outbox.py` — раскладка изменений в поток domain events, атомарно со сверкой;
* `app/integration_events.py` — публичный контракт изменений и хендлер domain → integration;
* `app/integration_publisher.py` — publisher: очередь `case_changes`, at-least-once;
* `app/api/` — HTTP-роуты: запуск обхода, чтение карточек, чтение событий, состав
  регулярного обхода;
* `app/tasks.py` — Celery-задачи, ночной прогон дел на мониторинге, жизненный цикл
  `SearchTask`, учёт капчи;
* `app/admin.py` — админка на `/admin`;
* `app/validators.py` — правила identity (канонизация адресов, синтетические УИД);
* миграции alembic: initial под всю схему, флаг регулярного обхода, очередь сообщений
  наружу.

Работает вся цепочка от HTML до БД:

```
HTML -> парсер -> ParsedCase -> sync_case -> PostgreSQL + CaseChanges
```

Работает вся цепочка целиком: `discover_case(source_url=…)` сходит на портал, определит
суд, УИД и номер дела, выберет парсер по вёрстке и сохранит карточку.

`docker-compose up` поднимает инфраструктуру и пять контейнеров core_v2: `api`, два
воркера (`urgent`, `regular`), `beat` и `outbox-publisher`. Планировщик нужен в
ЕДИНСТВЕННОЙ реплике: два beat поставят ночной обход дважды, то есть удвоят расход прокси
и оплаченной капчи.

Пустых каталогов «на будущее» здесь нет намеренно: папка появляется вместе с кодом,
который в неё ложится.

## База данных

Своя база — `soroka_core_v2`, отдельная от базы старого core. Причина не в
предпочтениях: `alembic_version` это однострочная таблица, поэтому две независимые
истории миграций в одной базе невозможны. Побочная польза — старый core можно держать
запущенным рядом и сверять поведение.

Заводится скриптом `deploy/postgres/init.sql` при первой инициализации кластера.

```
alembic upgrade head
```

История миграций начинается с нуля: 27 миграций старого core сюда не копируются,
первая ревизия описывает целевое состояние моделей сразу, без колонок старого core.

## Про парсеры и golden-файлы

Парсеры содержат накопленное знание о реальных судебных сайтах: терпимость к латинским
двойникам в русских метках («Cудья» с латинской C), поиск колонок по тексту шапки, а не
по номеру, порядок проверки меток, обход скрытых мобильных клонов таблиц. Ни одно из этих
правил не выводится из общих соображений — каждое появилось из-за конкретной страницы
конкретного суда.

Поэтому в `tests/golden/` лежат снимки вывода **старых** парсеров по всем 80 сохранённым
страницам, снятые до переноса, а `tests/test_parsers_golden.py` прогоняет по тем же
страницам новые парсеры и требует совпадения. Расхождение — это найденная регрессия, а не
повод пересобрать golden.

Единственное намеренное расхождение задокументировано в самом тесте, в константе
`PUBLISHED_AT_ADDED_TO_TYPE_A`.

## Клиенты судов: клиент на способ доступа, а не на вёрстку

Три клиента, потому что есть три способа добраться до карточки: форма поиска по УИД
(Москва), прямая ссылка с прохождением капчи (msudrf), прямая ссылка с ожиданием
отрисовки (Петербург). Вёрсток при этом четыре — движок msudrf отдаёт две.

**Новая вёрстка добавляет парсер, а не клиента.** Новый клиент нужен только тогда, когда
меняется сам способ добраться до страницы. В старом core у msudrf было два клиента, и
второй состоял целиком из одной строки `page_type = "C"`.

Прокси клиент не арендует — получает готовый аргументом. Аренда живёт в
`app/services/proxy_pool.py`, потому что открывает сессию БД, а пакет браузера про базу
знать не должен.

## Identity: чем опознаём карточку

Ключ карточки — тройка «УИД + суд + номер дела». От неё считаются детерминированные uid
всех дочерних строк, поэтому сменить ключ существующей карточки значит перестать узнавать
её события и документы.

Три обычные функции в `app/services/identity.py` и `app/courts/base.py`, без классов:
`find_uid`, `resolve_case_code`, `resolve_case_uid`. У последней три шага, и порядок
обязателен: сохранённый УИД карточки важнее найденного на странице. Это единственное, что
делает самодельный ключ (`synthetic_uid`) безопасным — портал может дозаполнить УИД
позже, и подмена ключа устроила бы волну ложных удалений.

## Discovery и re-sync — два входа в один путь

`app/services/discovery.py`:

```
discover_case(uid=...)         дело неизвестно, пришло УИД      (портал с поиском)
discover_case(source_url=...)  дело неизвестно, пришло ссылкой  (портал без поиска)
resync_case(case_id)           дело известно, берём его источник
```

Дальше все три идут одной дорогой до одного и того же `sync_case`. Отдельного «refresh»
рядом с «sync» нет: они различаются ровно тем, откуда взялся адрес или УИД.

Ни Celery, ни `SearchTask` внутри нет. Обход падает исключением, а решать, повторять ли
поход, — дело входной точки; отличить временный отказ от окончательного помогает
`is_terminal(exc)`.

## Outbox: это не уведомления

Строка `outbox_event` означает ровно одно: **core обнаружил, что на портале что-то
изменилось.** Не «надо кому-то отправить»: core не знает ни пользователей, ни подписок,
ни каналов. Поэтому в payload нет и не должно быть ни `user_id`, ни `sent`, ни
`delivered`.

Два свойства, ради которых всё устроено именно так:

* **атомарность** — события пишутся в ТОЙ ЖЕ транзакции, что и изменение карточки
  (`app/services/discovery.py`). Событие не может потеряться и не может появиться без
  изменения; откат уносит оба;
* **baseline** — первый обход событий НЕ создаёт. Вся карточка на нём формально «новая»,
  но это не изменения: так на портале было и до нас.

Читаются события через `GET /cases/{case_id}/events?since=<момент>`. В старом core такого
эндпоинта не было вовсе — события писались, но прочитать их можно было только глазами в
админке.

## Два представления одного изменения

Из одного и того же diff'а пишутся ДВЕ таблицы, в одной транзакции:

```
CaseChanges
    │ changes_to_events()        app/outbox.py
    ▼
DomainEvent
    ├──▶ outbox_event               домен-лог: богатый payload, append-only,
    │                               читается по HTTP курсором по created_at
    └──▶ integration_outbox_event   публичный контракт: тип, id дела, id сущности,
         to_integration_events()    версия, момент. published_at. Едет в RabbitMQ
```

Дублирование сознательное, и причина одна: **payload домен-лога меняется всякий раз, когда
парсер начинает отдавать новое поле, а клиентский сервис от таких правок ломаться не
должен.** Поэтому наружу уходит отдельное скудное представление, а полные судебные данные
клиент берёт по HTTP.

Соответствие «внутренний тип → публичное имя» задано явной таблицей
`INTEGRATION_TYPE_BY_DOMAIN` (`app/integration_events.py`). Пока она есть, внутренний enum
можно переименовать, и наружу это не просочится. Полноту таблицы проверяет тест.

Публикуются ВСЕ 16 типов: что показывать пользователю и о чём писать письмо, решает
клиентский сервис — он знает подписки и настройки, а core не знает ни того, ни другого.

Доставка **at-least-once**: публикация в брокер и `UPDATE published_at` — две операции, и
между ними процесс может умереть. Идемпотентность обеспечивает читающий, у него есть
неизменный id сообщения.

Ловушка на будущее: `entity_id` берётся из ORM-объекта, а у новых строк id появляется
только после flush. Поэтому `to_integration_events` зовётся ПОСЛЕ
`OutboxEventRepository.emit` — перепутанный порядок оставит `entity_id` пустым молча.

## Publisher: как изменения уезжают наружу

Отдельный процесс `python -m app.integration_publisher` (контейнер
`core-v2-outbox-publisher`):

```
take_unpublished(100)  →  опубликовать  →  published_at = now()  →  коммит  →  спать 1 с
```

Топология: durable exchange `soroka.case_changes` (direct) + durable очередь
`case_changes`, сообщения persistent. Все три флага нужны вместе: порознь они не значат
ничего, и перезапуск брокера стирал бы накопленное — а в outbox эти сообщения уже помечены
опубликованными, то есть изменения пропали бы навсегда и молча.

Отдельный процесс, а не часть обхода, чтобы сохранение судебных данных не зависело от
доступности брокера: упал RabbitMQ — дело, за которым мы честно сходили на портал, всё
равно сохранится, а сообщение уедет позже.

**Порядок операций обратный интуитивному: сначала публикуем, потом отмечаем.** Наоборот
означало бы потерю сообщения при падении; так — в худшем случае дубль, а его читающий
отбросит по `id`. Из двух неприятностей выбрана обратимая.

Порция, упавшая на середине, помечает ровно свой успешный префикс: `publish_batch` ошибку
ВОЗВРАЩАЕТ, а не бросает — брошенное исключение откатило бы транзакцию вместе с отметками.

SIGTERM (`docker compose stop`) доводит текущую порцию и выходит. Без этого процесс умирал
бы посреди порции, и каждый деплой давал бы дубли.

Реплика нужна одна; несколько не сломают — порция берётся через `FOR UPDATE SKIP LOCKED`.

Проверить руками:

```bash
docker compose up -d core-v2-outbox-publisher
docker compose logs -f core-v2-outbox-publisher
docker compose exec rabbitmq rabbitmqctl list_queues name messages
```

Очередь видно и в Management UI: http://localhost:15672.

## Регулярный обход

Раз в сутки `sync_monitored_cases` (`app/tasks.py`) набирает дела с флагом
`Case.is_on_monitoring` и ставит каждое на обычный повторный обход в очередь `regular`.
Своего пути синхронизации у мониторинга нет — он зовёт тот же `enqueue_case_resync`, что
и ручной прогон из админки.

Флаг ставит не core: его выставляет клиентский сервис запросом `PUT /monitoring/cases` с
ПОЛНЫМ списком id («после этого запроса на мониторинге ровно эти дела»). Операция
идемпотентна, повторный запрос с тем же списком меняет 0 строк. Пустой список отклоняется
с 409 без `?force=true`: пустое тело — самая вероятная форма аварии на стороне клиента, а
снятое зря дело перестаёт обновляться молча.

Флаг живёт на КАРТОЧКЕ, а не на подписке: на дело с тремя подписчиками мы всё равно идём
один раз. Поход стоит прокси и оплаченной капчи, и он не должен множиться на число
заинтересованных.

Дела разносятся по времени (`MONITORING_SPACING_SECONDS`, по умолчанию 60 с). Это не
вежливость к порталу: без разноса тысяча дел уходит в очередь одновременно, воркеры
разбирают её вперегонки, прокси кончаются, и деньги за капчу тратятся на попытки, которые
упадут по таймауту.

Настройки — `MONITORING_HOUR` (час прогона, UTC), `MONITORING_SPACING_SECONDS`,
`MONITORING_BATCH_LIMIT` (0 — все дела). Подробнее — `ARCHITECTURE.md`, вопрос 24.

## Что где лежит

```
HTTP / Celery      app/api/, app/tasks.py, app/admin.py   тонкие входные точки
оркестрация        app/services/discovery.py              два входа, один путь
сверка             app/services/case_sync.py              единственная запись в БД
события            app/outbox.py                          что изменилось (домен-лог)
контракт наружу    app/integration_events.py              что из этого уедет клиенту
доставка наружу    app/integration_publisher.py           отдельный процесс, RabbitMQ
разбор             app/parsers/                           HTML -> ParsedCase
поход на портал    app/courts/, app/browser/, app/captcha/
данные             app/models/, app/repositories/
```

Читать сверху вниз: каждый слой знает только тот, что ниже. Задача не знает, как устроен
портал; обход не знает про Celery и `SearchTask`; парсер не знает, откуда взялась
страница; клиент суда не знает, что с ней будут делать.

## Тесты и запущенный publisher

`tests/test_integration_publisher.py` заводит настоящие строки в `integration_outbox_event`
и проверяет, что порция взяла ровно их. Запущенный рядом `core-v2-outbox-publisher`
разбирает те же строки первым, и тесты падали бы через раз.

Модуль это замечает сам — кладёт пробную строку, ждёт полторы секунды и, если её кто-то
опубликовал, пропускается с внятной причиной. Чтобы прогнать их по-настоящему:

```bash
docker compose stop core-v2-outbox-publisher
```

## Правило про async

Все роуты FastAPI объявлены обычным `def`, а не `async def`, и так должно остаться.
Походы на порталы судов идут через Playwright **sync** API, а `sync_playwright()`
падает внутри работающего event loop. FastAPI выполняет обычный `def` в отдельном
потоке — там event loop'а нет. Первый же `async def` на пути до похода в суд сломает
это молча и не сразу, поэтому правило закреплено тестом
(`tests/test_skeleton.py::test_all_routes_are_sync`).
