# Characterization tests старого `services/core`

Фиксируют поведение старого core **до** переноса в `core_v2` — то, что ТЗ §29 называет
Phase 2. Это не тесты «правильности»: они закрепляют то, как код ведёт себя сейчас, чтобы
после переноса любое расхождение было видно.

## Почему отдельный каталог

Правило миграции №1 запрещает менять `services/core`. Добавление файлов в его `tests/` —
это тоже изменение. Поэтому каталог свой, а пакет `app` подтягивается через `sys.path`
в `conftest.py`.

Дополнительно это решает будущую проблему: в `core_v2` появится пакет с тем же именем
`app`, и импортировать два одноимённых пакета в одном процессе нельзя. Поэтому сравнение
«старый парсер против нового» в Phase 5 идёт **через golden-файлы**, а не через
одновременный импорт.

## Запуск

Из корня репозитория:

```
.venv310\Scripts\python.exe -m pytest services/characterization -q
```

Без тестов, требующих БД:

```
.venv310\Scripts\python.exe -m pytest services/characterization -q -m "not db"
```

Окружение: Python 3.10 + `services/core/requirements.txt` (venv лежит в корне
репозитория, `.venv310`). Тестам с маркером `db` нужен настоящий PostgreSQL — SQLite не
подойдёт, потому что `OutboxEvent.payload` это JSONB, а пул прокси использует
`FOR UPDATE … SKIP LOCKED`.

## Состав

| Файл | Что фиксирует |
|---|---|
| `snapshot.py` | сериализация вывода парсера в стабильный JSON с сохранением типа значения |
| `generate_golden.py` | пересборка golden-файлов |
| `golden/parser_{A,B,C,D}.json` | полный вывод каждого парсера на каждой из 80 страниц |
| `golden/detect_page_type.json` | определение вёрстки msudrf по каждой странице |
| `test_parsers_golden.py` | сверка с golden + отдельные тесты на наличие/отсутствие ключей (риск R1) |
| `test_identity_golden.py` | uid, card_key, synthetic_uid, канонизация URL, локальное время против UTC |
| `test_sync_and_outbox.py` | `update_case`: baseline, нулевой diff, new/updated/removed, атомарность outbox |

## Про golden-файлы

Каждый парсер прогоняется по **каждой** странице, а не только по «своим». Так фиксируется
и поведение на чужой вёрстке — оно не абстрактное: строка заголовка, протёкшая в `tbody`,
приводила к тому, что C-страница, разобранная как B, кладёт текст заголовка в `status` и
обходит охранник `_parse_is_empty`.

Сериализация различает `date` и `datetime` (`{"__date__": …}` против
`{"__datetime__": …}`), потому что календарная дата обязана остаться датой. Списки никогда
не сортируются: порядок строк документов участвует в identity через `occurrence`.

**Пересобирать golden имеет право только тот, кто осознанно меняет поведение парсера**, и
только вместе с записью `OLD → NEW → reason` в `services/core_v2_AUDIT.md`. В остальных
случаях расхождение с golden — это найденная регрессия, а не повод перегенерить файл.

## Что осталось непокрытым

- **Тип A характеризован всего двумя страницами** из 80: сохранённых карточек портала
  мировых судов Москвы (mos-sud.ru) в `html_examples/` только две. Тип D — семью.
  Это не дефект тестов, а нехватка фикстур; при переносе типа A уверенность ниже,
  чем при переносе B.
- Походы в сеть (`CourtClient`), капча и прокси здесь не покрыты — они уже покрыты
  тестами старого core (`test_msudrf_court.py`, `test_spb_court.py`, `test_proxy_pool.py`
  и др.), которые переносятся в Phase 6.
- `mir_court_list_full.html` исключён: это не карточка дела, а выгрузка списка судов
  с sudrf.ru в windows-1251 для `scripts/build_courts_json.py`.
