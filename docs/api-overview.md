# Soroka — что отдаёт API и что из этого можно показать

Документ для постановки задачи дизайнеру (в т.ч. как исходник промта для Figma).
Описывает **только API сервиса `core_v2`** — источник всех данных о делах. Это
единственное, что физически есть у фронта: если поля нет в этом документе, нарисовать его
не из чего.

Одна вещь, которая определяет границу: core знает суды и дела, но НЕ знает пользователей.
В нём нет ни аккаунтов, ни подписок, ни «моих дел», ни доставки уведомлений — всё это
живёт в сервисе поверх него. Поэтому и списка дел здесь нет: список принадлежит тому, кто
знает, чьи это дела.

---

## 1. Суть сервиса

Soroka следит за судебными делами вместо человека.

Пользователь отдаёт сервису **ссылку на карточку дела** на сайте суда (или **УИД** дела —
сквозной идентификатор вида `77MS0466-01-2026-003751-93`). Сервис сам заходит на портал
суда, разбирает страницу и складывает содержимое карточки в свою базу. Дальше он
**переобходит эту страницу раз в сутки** и сравнивает с тем, что было: появилось новое
событие, назначили заседание, изменился результат — это изменение фиксируется.

Зачем: сайты судов не умеют уведомлять. Чтобы узнать, что по делу что-то произошло,
человек должен вручную открывать страницу суда и глазами сравнивать таблицы.

Два факта, которые определяют почти весь UX:

1. **Поход в суд медленный.** Одно получение страницы — 25–35 секунд: прокси, платная
   капча, ретраи. Поэтому добавление дела **асинхронное**: API сразу отдаёт `task_id`
   и статус «в работе», а результат появляется через полминуты-минуту. Экран добавления
   обязан уметь состояние ожидания.
2. **Единица учёта — не «дело», а КАРТОЧКА дела.** Это тройка «УИД + суд + номер дела».
   По одному УИД карточек бывает несколько: дело шло по инстанциям (мировой участок →
   районный суд) или по одному УИД прошло приказное производство и следом исковое.
   Поэтому поиск по УИД может вернуть **список** карточек, а не одну.

Справочник судов — **7747 записей** по всем регионам РФ (мировые, общей юрисдикции,
апелляционные, кассационные). Реально разбирать сейчас умеем не все порталы — часть
запросов законно отклоняется с текстовым объяснением (см. §3.1).

## 2. Карта эндпоинтов

| Метод | Путь | Смысл |
|---|---|---|
| `POST` | `/search_case` | добавить дело: принять ссылку или УИД, завести фоновую задачу |
| `GET` | `/search_case/tasks/{task_id}` | статус фоновой задачи (её опрашивают, пока дело ищется) |
| `GET` | `/cases?ids=1,2,3` | **витрины нескольких дел** одним запросом — для страницы «мои дела» |
| `GET` | `/cases/{case_id}` | **полная карточка дела** со всеми вложенными сущностями |
| `GET` | `/cases/{case_id}/summary` | лёгкая витрина одного дела |
| `GET` | `/cases/{case_id}/events` | поток обнаруженных изменений по делу |
| `PUT` | `/monitoring/cases` | какие дела держать на регулярном обходе |
| `GET` | `/ping` | health-check |

Чего в API **нет** (важно для дизайна — этого не нарисовать):
поиска и фильтрации по делам, пагинации, пользователей и прав, уведомлений, ленты
изменений как отдельного ресурса, текстов и файлов документов, справочника судов как
эндпоинта.

Список дел клиент **собирает сам** из своих подписок: `GET /cases?ids=` отдаёт витрины
пачкой, но какие именно id спрашивать, знает только он.

## 3. Эндпоинты подробно

### 3.1. `POST /search_case` — добавить дело

Запрос:

```json
{ "query": "https://95.mo.msudrf.ru/modules.php?name=sud_delo&op=cs&case_id=...", "force": false }
```

`query` — одно поле на оба способа: ссылка **или** УИД. Что прислали, сервер понимает сам
по схеме адреса. Ссылка — универсальный путь; поиск по УИД работает только у части
порталов (сейчас — мировые суды Москвы).

Ответ:

```json
{
  "status": "processing",
  "case_id": 1042,
  "case_ids": [1042, 1188],
  "task_id": 77,
  "message": null
}
```

**`status` — пять исходов, и каждый требует своего вида в интерфейсе:**

| `status` | Что произошло | Что показать |
|---|---|---|
| `exists` | дело уже разобрано (его добавил кто-то раньше) | сразу открыть карточку, ожидания нет |
| `processing` | заведена фоновая задача, идём в суд | экран/строка ожидания, поллинг задачи |
| `invalid_query` | пустая строка или не адрес | ошибка поля ввода |
| `invalid_uid` | УИД не того формата | ошибка поля ввода |
| `link_required` | суд опознан, но поиска по УИД у него нет | подсказка «пришлите ссылку», с примером |
| `unsupported_court` | суда нет в справочнике либо портал пока не поддержан | объяснение + название суда |

`message` — **готовый человеческий текст отказа**, приходит с сервера. Его надо показывать
как есть, а не сочинять свой. Примеры реальных формулировок:

- `«Судебный участок № 235 района Хамовники: поиск по УИД на этом портале не поддерживается. Пришлите ссылку на карточку дела, например https://…»`
- `«Суда с сайтом 95.mo.msudrf.ru нет в справочнике судов.»`
- `«Судебный участок № 95: портал 95.mo.msudrf.ru пока не поддержан.»`

`case_ids` — все уже известные карточки этого УИД. Может прийти **вместе с** `task_id`:
что-то уже нашлось, а поиск всё равно запущен. Значит, интерфейс должен уметь показать
одновременно «вот что уже есть» и «ищем дальше».

### 3.2. `GET /search_case/tasks/{task_id}` — состояние поиска

```json
{
  "task_id": 77,
  "uid": "77MS0466-01-2026-003751-93",
  "source_url": "https://…",
  "status": "running",
  "case_id": null,
  "attempts": 2,
  "last_error": "captcha timeout"
}
```

`status`: `pending` (в очереди) → `running` (идём в суд) → `success` | `failed`.

`uid` **пустой**, пока дело завели ссылкой и до портала ещё не дошли: УИД становится
известен только с полученной страницы. То есть в состоянии ожидания дело нечем назвать,
кроме ссылки — это надо учесть в вёрстке «ищем дело». Он останется пустым и после
успешного поиска, если портал делу УИД не присваивал (см. §4.1).

`attempts` — число попыток зайти на страницу; `last_error` — техническая строка ошибки
(«403», «captcha timeout»), для пользователя её лучше прятать под «подробности».

### 3.3. `GET /cases/{case_id}` — полная карточка

Главный экран сервиса. Возвращает дело и **восемь вложенных коллекций**. Структура:

```json
{
  "id": 1042,
  "uid": "77MS0466-01-2026-003751-93",
  "code": "05-0444/1/2026",
  "application_number": null,
  "incoming_number": null,
  "receipt_date": "2026-03-14",
  "registration_date": null,
  "first_instance_date": "2026-05-21",
  "first_instance_decision": "Удовлетворено, 21.05.2026",
  "decision_effective_date": "2026-06-25",
  "superior_case_number": "10-0014/2025",
  "category": "…",
  "status": "Рассмотрено",
  "created_at": "…", "updated_at": "…",
  "last_checked_at": "2026-08-09T03:04:11",
  "last_changed_at": "2026-05-21T03:07:52",

  "court": { "id": 12, "code": "77MS0466", "name": "Судебный участок № 463 …",
             "level": "mirsud", "region": "Москва", "base_url": "https://…" },
  "urls": [ { "url": "https://…", "last_success_at": "2026-08-09T03:04:11" } ],
  "judges": [ { "id": 5, "full_name": "Иванова И. И." } ],
  "sides":  [ { "id": 9, "full_name": "ООО «Ромашка»", "role": "Взыскатель", "type": "Истец" } ],
  "events": [ { "id": 712, "uid": "…", "event_date": "…", "state_description": "…" } ],
  "place_history": [ … ], "instances": [ … ],
  "documents": [ … ], "court_sessions": [ … ],

  "case_link_id": 4,
  "related_case_ids": [1188, 1301]
}
```

### 3.4. `GET /cases/{case_id}/summary` — витрина для списка

Намеренно лёгкая схема: полная карточка весит сотни килобайт на дело.

```json
{
  "id": 1042, "uid": "…",          // может быть null
  "code": "05-0444/1/2026",
  "status": "Рассмотрено",
  "last_checked_at": "…", "last_changed_at": "…", "updated_at": "…",
  "is_on_monitoring": true,
  "court": { … }
}
```

**Строка списка дел может состоять только из этих полей.** Ни сторон, ни судьи, ни
ближайшего заседания в витрине нет — если дизайн хочет их в списке, это отдельная
доработка бэкенда, и об этом надо договориться заранее.

### 3.5. `GET /cases/{case_id}/events`

Поток изменений, обнаруженных по делу. Параметры: `since` (момент, позже которого отдавать
события) и `limit`.

```json
[
  {
    "id": 8123,
    "event_type": "event_new",
    "payload": {"event_date": "2026-08-14T10:00:00+03:00",
                "state_description": "Судебное заседание"},
    "created_at": "2026-08-14T03:07:52+03:00"
  }
]
```

Что важно понимать про этот ресурс:

* **это НЕ уведомления.** Строка означает «на портале это изменилось», а не «покажи это
  пользователю». Кому что показывать и что из этого считать поводом написать — решает
  тот, кто эти события читает;
* **первый обход дела событий не даёт.** На нём вся карточка формально «новая» — десятки
  строк истории, заседания, документы, — но это не изменения: так на портале было и до
  нас. Значит экран «что нового по делу» у только что добавленного дела будет пуст, и это
  правильное состояние, а не ошибка загрузки;
* **`event_type` — закрытый список** (в отличие от `status` карточки): 16 значений вида
  `event_new`, `session_new`, `document_new`, `case_field_changed`. По нему можно строить
  иконки и тексты;
* `payload` зависит от типа события — состав полей у «нового заседания» и «изменилось поле
  дела» разный;
* `created_at` служит курсором: запомнить момент последнего показанного события и прийти
  с ним снова. Сравнение строгое, повторов не будет.

Чего в событии НЕТ и не будет: получателя, признака «отправлено», статуса доставки. Core
не знает пользователей.

### 3.6. `GET /cases?ids=1,2,3` — витрины пачкой

То же, что `/cases/{id}/summary`, но сразу по нескольким делам и одним запросом. Ровно под
экран «мои дела»: без этой ручки страница с тридцатью подписками стоила бы тридцать
последовательных HTTP-запросов.

```json
[ { "id": 10, … }, { "id": 17, … } ]
```

Что важно для интерфейса:

* **отсутствующие id молча не попадают в ответ, и это не ошибка.** Список — не карточка:
  «одного из тридцати дел уже нет» не причина не показать остальные двадцать девять.
  Заметить пропажу можно, сравнив длину ответа с числом запрошенных id;
* порядок — по возрастанию `id`, а не такой, в каком их прислали;
* не больше 500 id за запрос; мусор в `ids` — 422, а не короткий список.

### 3.7. `PUT /monitoring/cases` — за какими делами следить

Ручка не для интерфейса: её зовёт сам клиентский сервис, когда у него меняются подписки.
Тело — ПОЛНЫЙ список: «после этого запроса на регулярном обходе ровно эти дела».

```json
{ "case_ids": [10, 17, 481, 922] }
```

```json
{ "monitored": 4, "added": 1, "removed": 0, "unknown_ids": [] }
```

* `added`/`removed` — сколько дел реально переключилось. Операция идемпотентна: повторный
  запрос с тем же списком даёт `0`/`0`;
* `unknown_ids` — присланные id, которых в core нет. Обычно пусто; непустое означает
  подписку на дело, которого уже (или ещё) не существует;
* **пустой список отклоняется с 409** без `?force=true`. Пустое тело — законное состояние
  «ни на что больше не подписаны», но оно же самая вероятная форма аварии на стороне
  клиента, а от правды её в запросе не отличить.

## 4. Сущности и поля

### 4.1. Дело (карточка) — центральная сущность

| Поле | Что это | Нюанс для интерфейса |
|---|---|---|
| `uid` | УИД дела, `77MS0466-01-2026-003751-93` | длинный, моноширинный, просится в «копировать». **Может быть `null`** — см. ниже |
| `code` | номер дела/материала, `05-0444/1/2026`, `М-2342/463/2026` | это то, как дело называет человек — заголовок карточки |
| `status` | текущее состояние словами | **свободный текст с портала, не enum** — «Рассмотрено», «Назначено судебное заседание». Длина непредсказуема, цветовую схему по нему строить нельзя |
| `category` | категория дела | свободный текст, бывает очень длинным |
| `receipt_date` / `registration_date` | дата поступления / регистрации | **взаимоисключающие**: у гражданских дел одна, у КоАП другая. В макете это одна строка, а не две |
| `first_instance_date` | дата рассмотрения в 1-й инстанции | |
| `first_instance_decision` | решение строкой как есть: `«Удовлетворено, 21.05.2026»` | дата уже внутри строки, отдельно её не выделяем |
| `decision_effective_date` | дата вступления в силу | |
| `superior_case_number` | номер дела в вышестоящей инстанции | это номер **другого** дела, не путать с `code` |
| `application_number`, `incoming_number` | номер заявления / входящего | часто пустые |
| `last_checked_at` | когда последний раз **ходили проверять** | ставится на каждом обходе, даже холостом |
| `last_changed_at` | когда на портале последний раз **реально что-то изменилось** | это и есть «дата обновления дела» для пользователя |
| `updated_at` | служебное поле строки в БД | **пользователю не показывать**: двигается на каждом обходе |

Про две даты: их надо показывать **обе и рядом**. «Дело не менялось три месяца» и «дело
три месяца не проверяли» — разные вещи, и вторая означает, что что-то сломалось.

**УИД есть не у всех дел.** Его начали присваивать примерно с 2021 года, поэтому у
архивных дел (а на отдельных порталах — и у свежих) на карточке суда УИД нет вовсе. Такие
дела сервис всё равно заводит и мониторит: внутри он считает им идентификатор сам, от
ссылки, но наружу его не отдаёт — в API у такой карточки `uid: null`. Значит, **`uid`
нельзя использовать как заголовок или ключ карточки в интерфейсе**: заголовок — это `code`,
ключ — `id`. Поиск такого дела по УИД тоже невозможен: искать его можно только ссылкой.

Почти все поля, кроме `code` и суда, — **опциональные**. Пустых значений в реальной
карточке много, макет должен выглядеть прилично, когда заполнена треть полей.

### 4.2. Суд (`court`)

`code` (`77MS0466`), `name` (`Судебный участок № 463 района …` — длинный),
`level` (`mirsud` | `general` | `appeal` | `kas` — мировой / общей юрисдикции /
апелляционный / кассационный), `region` (субъект РФ), `base_url`.

Суд у карточки **ровно один**. Номер в коде и номер участка в названии **не всегда
совпадают** — показывать надо название, а не код.

### 4.3. Ссылки (`urls`) — список

На одну карточку ведёт несколько адресов: http и https, другой порядок параметров,
сменившийся после переезда участка адрес. Поля: `url`, `last_success_at` (когда по этому
адресу последний раз удалось получить страницу; `null` — ни разу).

В интерфейсе это, скорее всего, одна кнопка «открыть на сайте суда» (берём рабочий адрес),
а полный список — под «показать все» или вовсе только в отладке.

### 4.4. Судьи (`judges`) — список

Только `full_name`. Судей у дела **может быть несколько**.

### 4.5. Стороны (`sides`) — список

- `full_name` — ФИО человека или название организации;
- `role` — роль **как её называет портал**: «Истец», «Взыскатель», «Должник»,
  «Привлекаемое лицо», «Подсудимый», «Обвиняемый», «Административный истец»… Словарь
  открытый, это свободный текст;
- `type` — грубая классификация для группировки и фильтров: `Истец` | `Ответчик` | `Другое`.

То есть стороны логично группировать по `type` (две-три колонки/секции), а подписывать
точной ролью из `role`.

### 4.6. События — «Движение дела» (`events`) — список

Главная таблица карточки, по ней и детектятся изменения.

- `id` — id строки. По нему клиентский сервис узнаёт СВОЮ строку: об изменениях он узнаёт
  сообщениями, где сущность названа этим же id (`entity_id`), и без него может показать
  «в деле что-то поменялось», но не подсветить конкретную строку. То же у `place_history`,
  `documents` и `court_sessions`;
- `uid` — детерминированный ключ строки, стабильный между обходами; служит сверке, а не
  показу. Одно другое не заменяет;
- `event_date` — дата события (всегда есть);
- `state_description` — описание состояния, длинный текст;
- `document_str` — название документа-основания **текстом** (ссылок на портале обычно нет);
- `published_at` — «Дата размещения» на портале, бывает пустой.

Это хронология дела. Естественная форма — вертикальный таймлайн или таблица, сверху новое.
Количество: от одной строки до нескольких десятков.

### 4.7. Судебные заседания (`court_sessions`) — список

- `session_date` — **дата и время** (`30.07.2026 16:50`);
- `place` — «зал»: номер участка и адрес;
- `stage` — «Судебное заседание», «Беседа»;
- `result` — **пустой у будущего заседания**, потом появляется «Отложено» /
  «Рассмотрение завершено»;
- `basis` — основание, например «Неявка подсудимого».

Заседания делятся на прошедшие (есть `result`) и **будущие (result пуст)**. Ближайшее
будущее заседание — самая ценная информация на всей карточке: это дата, к которой человеку
надо готовиться. Просится в отдельный акцентный блок наверху, а не в общую таблицу.

### 4.8. История местонахождения (`place_history`) — список

`place_date`, `place_description` (где физически лежит дело), `comment`. Второстепенная
таблица, обычно короткая.

### 4.9. Документы (`documents`) — список

`document_date`, `document_type`. **Только метаданные.** Ни текста, ни файла, ни ссылки на
скачивание сервис не хранит и хранить не планирует — «скачать документ» в макете быть не
должно. Строк по одной дате бывает до 21 одинаковой.

### 4.10. Инстанции (`instances`) — список

`instance_number`. Совсем простая сущность, одна строка на инстанцию.

### 4.11. Связанные дела

`case_link_id` — id группы связанных дел, `related_case_ids` — id **остальных** карточек в
этой группе. Так связываются карточки одного УИД в разных судах и разных производствах.
В интерфейсе — блок «связанные дела» со ссылками на другие карточки. Названий там нет,
только id: чтобы показать номера, фронту придётся дозапросить `summary` каждой.

## 5. Что можно нарисовать: инвентарь экранов

Ниже — только то, что обеспечено данными выше.

### Экран 1. Добавление дела
Одно поле ввода (ссылка или УИД) + кнопка. Состояния:
- ошибка формата (`invalid_query` / `invalid_uid`) — под полем;
- отказ с объяснением (`link_required` / `unsupported_court`) — текст `message` с сервера,
  в случае `link_required` рядом пример правильной ссылки;
- «уже есть» (`exists`) — переход на карточку;
- «ищем» (`processing`) — **ожидание 30–60 секунд**, с поллингом задачи. Показать нечего,
  кроме ссылки и `attempts`: УИД и номер дела ещё не известны;
- «нашли несколько карточек» — `case_ids` длиннее одного, надо предложить выбор.

### Экран 2. Список дел
Строка = `summary`: номер дела `code`, суд, `status` (свободный текст!),
«изменено» `last_changed_at`, «проверено» `last_checked_at`.

Тумблер «следить за делом» в интерфейсе есть, но его состояние — это ПОДПИСКА, и хранит
её клиентский сервис. Core он сообщает лишь итог: `PUT /monitoring/cases` с полным списком
дел, за которыми следит хоть кто-нибудь. Одно дело на трёх подписчиков обходится один раз.

В витрине дела флаг `is_on_monitoring` показывает, обходится ли дело в реальности. Он
нужен ровно для одного состояния интерфейса: «подписка есть, а дело не обходится» —
значит, что-то сломалось, и это надо показать, а не прятать.
Плюс состояния строки: «ищется» (задача ещё идёт), «не удалось получить» (`failed`).
Пустое состояние — «пока ни одного дела».

### Экран 3. Карточка дела — основной
Логичное деление на блоки:
1. **Шапка**: номер дела, УИД, суд (название + регион), `status`, тумблер слежения,
   «обновить сейчас», ссылка на портал суда;
2. **Ближайшее заседание** — акцентный блок, если есть `court_sessions` без `result`;
3. **Реквизиты дела** — даты, категория, решение первой инстанции, номера. Много
   опциональных полей, часть пустая;
4. **Участники** — судьи + стороны, сгруппированные по `type`, подписанные `role`;
5. **Движение дела** — таймлайн `events`;
6. **Заседания** — таблица `court_sessions` (прошедшие / будущие);
7. **Документы** — таблица `documents`, без скачивания;
8. **Местонахождение** — таблица `place_history`;
9. **Инстанции** — `instances`;
10. **Связанные дела** — `related_case_ids`;
11. **Служебное**: `last_checked_at`, `last_changed_at`, все `urls`.

### Экран 4. Управление слежением
Может быть не экраном, а тумблером на карточке и в списке. Плюс осмысленные пустые/ошибочные
состояния: «дело на мониторинге, но давно не проверялось».

## 6. Что дизайнеру важно знать заранее

1. **Свободный текст вместо enum.** `status` дела, `role` стороны, `stage` и `result`
   заседания — это то, что написал портал суда. Ни фиксированного набора значений, ни
   гарантированной длины. Компоненты должны переживать и «Рассмотрено», и строку на 120
   символов. Цветные бейджи по статусу дела строить не на чем.
2. **Половина полей пустая.** Нужны честные макеты «мало данных» и «много данных».
3. **Никаких файлов и текстов документов.** Только даты и типы.
4. **Асинхронность.** Между «добавил» и «увидел» проходит до минуты. Это отдельное
   состояние интерфейса, а не спиннер на секунду.
5. **Одна ссылка → несколько карточек.** УИД сквозной, карточек по нему бывает много.
6. **Две даты вместо одной.** «Проверено» и «изменено» — обе нужны.
7. **Русский язык, длинные названия.** Названия судов вида «Судебный участок № 463 района
   Хамовники города Москвы» — норма, они не помещаются в узкую колонку.

## 7. Открытые вопросы (на них API сейчас не отвечает)

- **Лента изменений.** Сервис хранит подробный diff каждого обхода (что за события
  добавились, какие поля дела поменялись, какие заседания появились), но **наружу через API
  его не отдаёт**. Если в дизайне нужен экран «что нового по делу» — это доработка бэкенда,
  и её надо запланировать до макетов.
- **Поиска и фильтров по делам не существует ни в каком виде.** Список дел клиент
  собирает сам: какие id ему интересны, знает только он, а витрины по ним отдаёт
  `GET /cases?ids=1,2,3` одним запросом.
- **Уведомлений нет** — в том смысле, что core не знает получателей и каналов. Но факт
  изменения он теперь сам отдаёт наружу: как только обход находит что-то новое, сообщение
  уезжает в очередь `case_changes` (RabbitMQ). Кому это показать и о чём написать письмо,
  решает клиентский сервис. Сообщение содержит только тип изменения, id дела и id
  сущности — судебные данные к нему идут отдельным запросом `GET /cases/{id}`.
