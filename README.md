# Soroka — мониторинг судебных дел

Пользователь отдаёт ссылку на карточку судебного дела (или его УИД). Сервис заходит на
портал суда, разбирает страницу, складывает содержимое в базу, а при следующем обходе
сравнивает с тем, что было, и фиксирует, что изменилось.

Зачем: сайты судов не умеют уведомлять. Чтобы узнать, что по делу что-то произошло,
человек должен вручную открывать страницу суда и глазами сравнивать таблицы.

## Что в репозитории

| Каталог | Что это |
|---|---|
| `services/core_v2` | **рабочий backend.** FastAPI + Celery: поход на портал, разбор, синхронизация, фиксация изменений |
| `services/core` | **старая версия, только для чтения.** Reference implementation: по ней сверяют поведение, её не запускают и не меняют |
| `services/characterization` | тесты, зафиксировавшие поведение старого core перед переносом |
| `services/core_v2_AUDIT.md` | разбор старого core: что перенесено, что удалено, чем рискуем |
| `services/client` | **клиентский сервис.** Django: пользователи, подписки, UI. Судебных данных не хранит |
| `deploy/` | init-скрипт БД и заготовка под Kubernetes |
| `docs/api-overview.md` | что отдаёт API — для постановки задач по интерфейсу |

Пользователи, подписки и UI живут в отдельном сервисе `services/client` (обычный Django).
Он обращается к core по HTTP и подписан на его очередь изменений. Старый Django-клиент был
удалён целиком; этот написан заново под другую границу ответственности.

## Граница ответственности

```
        клиентский сервис (в работе)
        пользователи, подписки, тарифы, UI, unread, доставка уведомлений
              │                                        ▲
      какие дела интересны                    что изменилось
      PUT /monitoring/cases                   RabbitMQ, очередь case_changes
              ▼                                        │
        core_v2
        суды, дела, поход на портал, разбор, синхронизация,
        регулярный обход, фиксация обнаруженных изменений
```

Полные судебные данные для показа клиент забирает по HTTP (`GET /cases/{id}`) и себе НЕ
копирует. Через очередь едет только факт: «по делу 481 появилось событие 712».

Одной строкой:

    клиент знает, какие дела интересны   →   core знает, как и когда их обновлять

Core не знает, КТО следит за делом: ни пользователей, ни подписок, ни каналов доставки в
нём нет. Он знает лишь, что за делом следят — по флагу `is_on_monitoring`, который ему
выставляет клиент, — и распоряжается расписанием обходов сам.

## Локальный запуск

```bash
docker-compose up --build
```

Поднимется одиннадцать контейнеров: `postgres`, `rabbitmq`, `redis`, `minio`,
`minio-init`, `core-v2-api`, `core-v2-worker-urgent`, `core-v2-worker-regular`,
`core-v2-beat`, `core-v2-outbox-publisher`, `client-web`, `client-consumer`.

`core-v2-beat` — планировщик ночного обхода дел на мониторинге. Он нужен в единственной
реплике: два beat поставят обход дважды, то есть удвоят расход прокси и оплаченной капчи.

`core-v2-outbox-publisher` — увозит найденные изменения в очередь `case_changes`. Отдельный
процесс, чтобы сохранение судебных данных не зависело от доступности брокера.

`client-consumer` — читает ту же очередь на стороне клиента. Соединение держится открытым,
поэтому изменение доходит до клиента через секунду после того, как его нашёл обход.

Дальше — накатить схему core и залить справочник судов (без строк `Court` не работает
ничего):

```bash
docker compose exec core-v2-api alembic upgrade head
docker compose exec core-v2-api python scripts/sync_courts.py
```

Схему клиентского сервиса контейнер накатывает сам при старте, но пользователя надо
создать руками:

```bash
docker compose exec client-web python manage.py createsuperuser
```

## Проверка

- Клиентский сервис: http://localhost:8001 — вход, «мои дела», добавление дела
- API core: http://localhost:8000/ping → `{"message": "pong"}`
- Документация API: http://localhost:8000/docs
- Админка: http://localhost:8000/admin (логин/пароль из `.env`)
- RabbitMQ UI: http://localhost:15672 — очередь `case_changes` обычно пуста: подписчик
  разбирает её сразу. Растущая очередь означает, что `client-consumer` не работает
- Цепочка целиком: `docker compose logs -f client-consumer`, затем изменить дело в core
- MinIO: http://localhost:9001

## Тесты

Тесты запускаются локально, вне docker. В корне есть готовый venv:

```bash
cd services/core_v2 && ../../.venv/Scripts/python.exe -m pytest -q
cd services/client  && ../../.venv/Scripts/python.exe -m pytest -q
```

Части тестов core нужен настоящий PostgreSQL. Без базы под рукой:

```bash
cd services/core_v2 && ../../.venv/Scripts/python.exe -m pytest -q -m "not db"
```

Тестам клиентского сервиса база нужна всегда — Django создаёт свою, `test_soroka_client`.

Подробнее — в `services/core_v2/README.md` и `services/client/README.md`.
